## 根因分类

主分类：**测试身份设计缺陷**。

不是产品缺陷：

- `events.id`、`actions.id` 和 `courses.id` 才是实体身份；title 只要求非空及长度合法，没有 Owner/date/title 唯一契约。两个不同 Event 合法同名。
- Today 本身以 `event.id` / `summary.action.id` 作为 React key，并把 Event UUID 放进 `/schedule/events/{event.id}`。产品没有把 title 当实体主键。
- V6 Fake advice 固定返回 `V6 cited linear algebra study`；同一测试复用 storage state 和同一 `app.sqlite`，所以第二轮后出现两个同名但 UUID、Course、Action、TimeRequest、Event lineage 均不同的事实，是预期的单 Owner 历史语义。
- 当前失败只来自 `getByRole('link', { name: '查看日程详情：V6 cited linear algebra study' })` 对 accessible name 作全局唯一假设。strict violation 正确暴露了该错误假设。

不是冻结契约歧义：

- 冻结计划同时明确了 single local Owner、desktop+iPhone deterministic full loop、Proposal/Confirm、semantic idempotency，以及 Course-linked Action、ACTIVE TimeRequest 和 accepted STUDY Event。
- Contracts 已明确提供 `CREATE_LEARNING_ACTION.action.id/courseId`、`scheduling.timeRequestId`、Daily Plan item 的 `timeRequestId` 和 decision 的 `scheduledEventId`。身份链并不缺失。
- Core 实现按该链写入：Learning Proposal 生成 Action/TimeRequest UUID；接受时写 `learning_actions`，并令 TimeRequest `origin={kind:'ACTION', entityId:action.id}`；Daily Plan decision 把 `scheduled_event_id` 绑定到该 TimeRequest；Today 再经 `event → proposal_decision → time_request.origin_id → learning_action.course_id` 回投 Course lineage。

静态 diff 结论：`apps/core/src/storage/migrations.ts` 只有 Git 的 LF/CRLF 提示，`git diff --exit-code -- apps/core/src/storage/migrations.ts` 为 0，**无实际 diff**。

## 三方案裁决

1. **每视口独立 DB — 拒绝。** 会把一个 Owner 在同一真实本地数据中的连续历史拆成两个隔离世界，不能证明第二视口在已有本地事实下仍完成全循环；也偏离当前 runner 一次创建一个 owned data directory/Core 的证据语义。
2. **Fake title 加 context identity — 拒绝。** viewport identity 不是学习建议的领域输入。把它编码进 Fake 内容只是让 title 暂时唯一，仍然把展示文本误当实体身份，并无必要地改变 Fake 行为。
3. **按 Event/Action/Course lineage 稳定 id 定位 — 采纳。** 复用已有 Contract UUID，不改生产边界，不改固定 Fake，不清数据，不引入第二 Owner；同时可直接证明没有重复物化。

## 不是用 `.first()` 掩盖重复写入的证明标准

通过标准不是“某个同名链接可见”，而是下列完整映射对每轮均成立且 cardinality 精确为 1：

```text
Course URL courseId
  = LEARNING Proposal change.action.courseId
  -> change.action.id
  = Today learningActions[actionId].courseId
  -> change.scheduling.timeRequestId
  = Daily Plan proposal item.timeRequestId
  -> Daily Plan decision.scheduledEventId
  = Today events[eventId].courseId
```

额外的跨轮 cardinality 证明：desktop 后固定 title 的 Action/Event 各 1 条；iPhone 后各 2 条；两条的 UUID 集合必须恰好等于两轮捕获集合，且两个 Course 各自仍只有 1 个学习 Action 和 1 个 STUDY Event。少一条表示链路未完成，多一条表示重复写入；两条同名本身不是失败。
