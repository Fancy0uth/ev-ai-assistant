## P1-A：WebP integrity

根因：旧 parser 把只有 `VP8X` canvas header 的 RIFF 容器当作可解码图像，没有要求 `VP8`/`VP8L` image-bearing payload，也没有校验扩展 feature bits 与 chunks 一致性。

RED：

```powershell
npm test --workspace @ev/core -- tests/course-import.test.ts -t "rejects malformed WebP RIFF and VP8X/VP8/VP8L chunks before persistence|rejects a VP8X-only WebP before persistence or any Vision call"
# exit 1: 1 failed / 1 passed / 7 skipped
# VP8X-only 期望 422，实际 201。
```

GREEN：测试使用离线生成的真实 1x1 `VP8X + ICCP + VP8` WebP 作为正例，并精确断言 VP8X-only 为 `422 IMAGE_DIMENSIONS_INVALID`、本地 artifact DB/files 为 0、Vision calls 为 0。Parser 现要求唯一实际 image chunk，校验 canvas 尺寸、RIFF/chunk/padding、VP8L header 和 feature/chunk 一致性，并确定性拒绝 animation。同一命令 exit 0：2 passed / 7 skipped。

## P1-B：crash-safe DELETE_PENDING recovery

根因：两阶段删除只在在线 delete 路径终结；进程在 DB 标记后或 unlink 后崩溃时，启动不会重放 pending 项。同时 terminal update 没有把 owner/id/still-pending 同时作为必须条件，`ENOENT` 也不是幂等成功。

RED：

```powershell
npm test --workspace @ev/core -- tests/course-import.test.ts -t "recovers DELETE_PENDING artifacts after crashes|keeps unsafe and failed artifact removals pending|terminalizes artifact deletion only"
# exit 1: 3 failed / 9 skipped
# restart 后两行仍 DELETE_PENDING；service 不存在 recoverPendingArtifactDeletes。
```

GREEN：仓储层 Owner-safe 枚举精确 id/owner/storage key，terminal update 要求 owner/id/still-pending。Artifact store 保留 root containment，仅 `ENOENT` 视为已缺席。启动恢复在 SQLite write transaction 外 unlink，随后用短 exact immediate transaction 终结；unsafe/EACCES 项保留 pending 并由 app logger 观察。测试覆盖 unlink 前/后崩溃、restart、unsafe key、foreign Owner/exact update、重复删除和 DB transaction 边界。同一命令 exit 0：3 passed / 9 skipped。

## P1-C：browser semantic idempotency

根因：Course import review 每次点击 extract/confirm 都调用 `crypto.randomUUID()`，因此在 Core 已提交但 transport/BFF/response parsing 丢失时，重试会变成新写入意图。

RED：

```powershell
npm test --workspace @ev/web -- tests/schedule-workspace.test.tsx -t "reuses separate extract and confirm keys|starts a new extract key|starts a new confirm key"
# exit 1: 1 failed / 2 passed / 3 skipped
# 四次不确定 extract 重试收到四个不同 UUID。
```

GREEN：组件使用现有 `createIdempotencyKey` 与 `isUncertainCoreWriteFailure`，为 extract/confirm 分别保留 `{idempotencyKey, body}`。transport/status 0、BFF 502 与 nominal-success schema parse 失败均复用原 key/body；成功或确定 Core error 清除，下一次语义尝试生成新 key。同一命令 exit 0：3 passed / 3 skipped。
