## New blocking finding

### V07-LINEAGE-015 — P1 — a reused nutrition source key can persist a non-verifying record and false license lineage

- **Path:** `apps/core/src/modules/nutrition/repository.ts:182-198,336-341`
- **Frozen requirement:** The full immutable source descriptor includes kind/id/version/dataset hash/redistribution/license decision (`design:674`); every descriptor/record hash is verified before persistence (`design:578`); every confirmed Meal must preserve source/version/dataset hash/record hash/unit/serving lineage (`design:784`).
- **Root cause:** `insertSourceSnapshot` inserts or ignores the full source row, but `findSourceSnapshot` identifies an existing row only by `(owner_id, source_kind, source_id, source_version, dataset_hash)`. It does not compare `redistribution`, `license_decision_id`, `adapter_kind`, or `evidence_kind`. After an ignored insert, every new food record is linked to whichever older row owns that partial key.
- **Focused reproduction:** In one in-memory database and one Owner, the first valid `APPROVED_LOCAL_DATASET` provider used `catalog/v1/<same hash>`, `redistribution=false`, `licenseDecisionId=license-A`. A second independently valid provider used the same kind/id/version/hash but `redistribution=true`, `licenseDecisionId=license-B`. Both provider records carried hashes correctly computed from their own full descriptors and passed the strict provider boundary. The second match response advertised source B, but its immutable snapshot read back source A. The stored record hash was `3a6bc93fa042f1dbf1993b16e26333e9e19dcdbb3ce875f7cacbcfb24da109a3`; recomputation from the persisted record returned `0362ab3bf95df349e3cf3994369c2c102851a75e54d07e7357511e719aee7110` (`hashMatches=false`).
- **Downstream result:** Selecting that snapshot and confirming succeeded with state `CONFIRMED`. The Meal's `FOOD_SNAPSHOT` lineage retained the non-verifying hash while the match response had advertised the different redistribution/license decision.
- **Impact:** A valid runtime configuration change can silently falsify immutable legal/source provenance and content-addressed record integrity. This is not a display-only discrepancy; it reaches an authoritative confirmed Meal.
- **Required repair:** Treat the full stored descriptor plus adapter/evidence fields as immutable for an existing source key. On collision, compare every field and fail transactionally before food snapshots/revision/Meal state can advance, or introduce an additive identity/schema that cannot alias distinct descriptors. Add a regression using two valid descriptors with the same current unique key and different legal metadata; require a controlled failure, no partial persistence, and no confirmable Meal.

The exact local invocation form was `node --import tsx --input-type=module -e "<inline in-memory two-provider probe>"`. The first attempt exited 1 before SQLite because it referenced the nonexistent `apps/core/src/db/database.ts`; after tracing the repository export to `apps/core/src/storage/database.ts`, two corrected probes exited 0 and produced the mismatch and successful confirmation above. No product file was changed.
