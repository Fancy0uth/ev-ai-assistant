## 最后一次 WebP 修复：独立结论

### 1. 仅有精确长度帧头的 VP8/VP8L 必须 422

`apps/core/src/modules/calendar/image-metadata.ts:139-170` 在 RIFF/chunk/feature/尺寸解析和 40M 像素算术限制之后，对 WebP 调用 `sharp(image, { failOn: 'error', limitInputPixels: MAX_PIXELS }).stats()` 做本地完整像素解码；解码失败映射为图片尺寸无效。`apps/core/tests/course-import.test.ts:201-239` 构造精确 10-byte VP8 frame header（总对象 30 bytes）和 5-byte VP8L header（总对象 26 bytes），两个响应均为 422 / `IMAGE_DIMENSIONS_INVALID`。

独立本地 Chromium 解码交叉检查（`about:blank`、无网络）结果：

```json
{"vp8Good":{"decoded":true,"width":2,"height":3},"vp8lGood":{"decoded":true,"width":2,"height":3},"vp8Header":{"decoded":false,"error":"InvalidStateError"},"vp8lHeader":{"decoded":false,"error":"InvalidStateError"}}
```

这证明失败夹具并非仅被 Sharp 特有策略拒绝，而是在独立浏览器解码器中同样不可解码。

### 2. 失败前没有 artifact 行、文件或 Vision 调用

`apps/core/tests/course-import.test.ts:229-239` 在两个 422 之后直接检查 `local_artifacts` 行数为 0、artifact 文件数为 0、受控 Vision `providerCalls` 为 0。上传本身不调用 Vision；`apps/core/src/modules/calendar/import-service.ts:72-90` 的执行次序为：5 MB 上限 → `await readImageMetadata` → 去重查询 → 文件写入 → artifact 行插入。因此解码失败发生在去重和任何持久化之前。

### 3. 良好 VP8/VP8L 可真实解码并按 2×3 上传

`apps/core/tests/course-import.test.ts:242-260` 先以 Sharp 对固定 VP8/VP8L fixture 做 `stats()`，再通过真实上传路由断言两个响应均为 201，且两个 artifact 都是 `image/webp`、`width=2`、`height=3`。独立 Chromium 也确认两个 fixture 的自然尺寸为 2×3。

### 4. 限制和解码顺序正确

- 5 MB 请求体限制：`apps/core/src/modules/calendar/import-service.ts:14,72-75`。
- RIFF/chunk/VP8X/VP8/VP8L 结构及特征一致性：`apps/core/src/modules/calendar/image-metadata.ts:66-137`。
- 单边最大 12,000、总像素最大 40,000,000：`apps/core/src/modules/calendar/image-metadata.ts:5-6,165-170`。
