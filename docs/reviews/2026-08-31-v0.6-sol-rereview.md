## Blocking findings

### P1-ARTIFACT-001 — VP8X-only non-image is still persisted as verified WebP

Evidence:

- `apps/core/src/modules/calendar/image-metadata.ts:79-81` treats the first `VP8X` chunk as sufficient to establish dimensions.
- `apps/core/src/modules/calendar/image-metadata.ts:98-101` returns those dimensions when the RIFF ends, without requiring a `VP8 `, `VP8L`, or valid animated image payload.
- `apps/core/tests/course-import.test.ts:124,132-142` constructs only `RIFF + WEBP + VP8X(10 bytes)`, expects upload `201`, and persists it as a 1×1 WebP.
- Fresh offline probe passed the exact 30 bytes to `readImageMetadata()` and installed Chromium `createImageBitmap()`. Core returned verified metadata (`width=1`, `height=1`); Chromium returned `InvalidStateError`.

Impact: a corrupt/non-decodable object crosses the private artifact trust boundary, is persisted, and can later be sent to an approved Vision adapter. This is the same security/correctness class as the immutable prior P1, so it cannot be marked closed merely because RIFF and chunk lengths are now checked.

Smallest repair contract: require an image-bearing payload consistent with the WebP container/feature bits before returning dimensions; reject the current 30-byte VP8X-only fixture with `IMAGE_DIMENSIONS_INVALID`; assert zero artifact rows/files and zero Vision calls. Keep the new RIFF/chunk-size/padding checks.

### P1-ARTIFACT-RECOVERY-002 — two-phase deletion has no startup recovery and is not crash-after-unlink idempotent

Evidence:

- The frozen contract requires startup recovery at `docs/superpowers/plans/2026-08-23-v0.6-learning-schedule-loop.md:251`.
- `apps/core/src/modules/calendar/import-service.ts:85-95` performs `ACTIVE -> DELETE_PENDING`, then unlink, then `DELETED`, but exposes no recovery operation.
- `apps/core/src/modules/calendar/artifact-store.ts:46-48` uses `unlink()` directly; `ENOENT` is treated as failure rather than successful already-absent terminal state.
- `apps/core/src/app.ts:116-117` runs only capability stale recovery. Repository/source search finds no enumerator or startup sweep for `DELETE_PENDING` artifacts.

Crash consequences:

1. Crash after `DELETE_PENDING` and before unlink retains the private image indefinitely because startup never retries it.
2. Crash after unlink and before `DELETED` leaves the row permanently pending: the next DELETE calls `unlink` on an absent file, returns 503, and never marks the row deleted.

Impact: the promised private-data deletion lifecycle is neither recoverable nor idempotent across the exact crash boundaries for which the two-phase state exists. This is a release-blocking local data-safety defect.

Smallest repair contract: add an Owner-safe repository iterator for pending rows; on startup retry only storage keys proven contained under the configured artifact root; treat `ENOENT` as successful absence; mark `DELETED` in a short transaction after each successful/already-absent unlink. Add deterministic crash-before-unlink, crash-after-unlink, restart, containment, foreign-owner, and repeated-delete tests. No file operation may enter a SQLite write transaction.

### P1-IDEMPOTENCY-UI-002 — import UI discards semantic keys after uncertain writes

Evidence:

- `apps/web/src/lib/core-client.ts:17-24` explicitly states that callers must retain the semantic action's key for transport loss, BFF 502, or an unreadable nominal success.
- `apps/web/src/components/schedule/course-import-review.tsx:17-27` generates `crypto.randomUUID()` inside every extract attempt and only records an error in `catch`.
- The same defect exists for confirmation at `course-import-review.tsx:46-57`.
- After a lost successful extract response, a new key bypasses the terminal replay branch at `apps/core/src/modules/calendar/import-service.ts:131-146` and reaches the changed-state conflict at `:147-150`.
- After a lost successful confirmation response, a new key reaches `import-service.ts:248-253` and returns `IMPORT_ALREADY_CONFIRMED`, not the committed response.
- `apps/web/tests/schedule-workspace.test.tsx:46-83` checks review gating/editing but has no uncertain-write same-key retry assertion.

Impact: a normal browser/BFF response loss can consume the sole Vision call or atomically create Course/Rule/Proposal, yet leave the user on stale UI state with no semantic replay path. Core's repaired idempotency cannot protect an official caller that always changes its key.

Smallest repair contract: retain separate extract and confirm keys across `isUncertainCoreWriteFailure()` outcomes; reuse them with the identical payload until a definite terminal response/error; clear only at a new semantic action boundary. Add component tests that simulate a committed-but-lost first response and assert identical retry key/payload plus recovered terminal UI for both commands.
