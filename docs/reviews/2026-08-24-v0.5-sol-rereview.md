## 4. P1-RECOVERY-001：损坏 Run 关联会被部分终结

### 精确位置

- `apps/core/src/modules/daily-planning/execution-unit-of-work.ts:144-151`：correlated Run 只按 `owner_id + idempotency_record_id + GENERATING + lease_token` 查找；
- 同文件 `:230-252`：只有 `if (run)` 才终结 Run/preflight，找不到 Run 不被判为不一致；
- 同文件 `:253-266`：无论是否找到 Run，仍终结 STARTED Provider log 与 idempotency snapshot；
- `apps/core/src/app.ts:148-158`：startup 直接接受该 sweeper 的成功结果；
- `apps/core/tests/v0.5-recovery-sweeper.test.ts:276-318`：现有 corruption test 只覆盖“Run 仍能关联、但 preflight 被删除”，没有覆盖 Run 关联本身损坏。

### 最小文件 DB 反例

临时 probe 使用 runner 外的独立临时文件 DB、Counting Provider、Counting SecretStore 和注入 clock；产品代码未修改。步骤：

1. 通过真实 Core API setup → prepare → approve；
2. 用 repository 建立正常 attempt 1 的 `IN_PROGRESS` idempotency、`GENERATING` Run、`CLAIMED` preflight 与 STARTED reservation；
3. 模拟损坏关联：

   ```sql
   update daily_plan_runs
   set idempotency_record_id = null
   where id = ? and owner_id = ?;
   ```

4. 关闭文件 DB，把 clock 推进到 lease 过期后，重新 `buildApp`；
5. startup 未报错，原始状态为：

   ```json
   {"idempotency":{"state":"FAILED","response_status":503},"run":{"status":"GENERATING"},"preflight":{"status":"CLAIMED"},"providerCall":{"status":"FAILED"},"providerCalls":0,"unprotectCalls":0}
   ```

实际命令：

```powershell

```

结果：exit 0，反例状态与断言一致。probe 与临时 DB 随后删除，工作树恢复干净。

### 风险与最小修复边界

这是确定性永久运行态：idempotency 已 FAILED，后续 startup 的查询只扫描 `IN_PROGRESS`，无法再收敛孤立 Run/preflight；same key replay 503 也不会触发修复。UI/后续逻辑仍可观察到不可能自动结束的 `GENERATING/CLAIMED`。

最小修复不需要新迁移或重构产品：terminal UoW 应从 `record.resource_id` 读取 owner-scoped preflight，再沿 `preflight.run_id` 验证 Run 的 owner、status、idempotency record 与 lease。只有“尚未建立业务 claim，且不存在 CLAIMED/GENERATING/STARTED 证据”可按无 Run 的合法窗口只终结 idempotency；若任一对象显示 execution 已开始而 correlation 不完整，必须抛错，使本次 terminal transaction 全回滚并让 `buildApp` fail closed。新增文件 DB test 至少应清空/篡改 `daily_plan_runs.idempotency_record_id`，断言启动失败且 Run/preflight/log/idempotency 四者全部保持原状态。
