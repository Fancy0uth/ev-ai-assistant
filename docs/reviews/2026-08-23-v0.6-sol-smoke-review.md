### P1

#### P1-IDEMPOTENCY-001 — Vision extract 的 claim 不是原子幂等事务，会留下永久 `EXTRACTING`，且成功请求无法稳定 replay

- 位置：`apps/core/src/modules/calendar/import-service.ts:123`、`:127`、`:133`、`:135`。
- 证据/复现：服务先在第 133 行单独把 import 从 `AWAITING_DISCLOSURE` 改成 `EXTRACTING`，再在第 135 行写 Owner 全局唯一的 `idempotency_key`；二者不在一个事务中，也不检查 capability-run update 的 changes。若该 key 已被同 Owner 的其他 capability run 占用，第 135 行触发唯一约束，import 已经停在 `EXTRACTING`，异常又发生在 provider `try/catch` 之前，无法回滚或终结。即使第一次成功，同 key/同 payload 重试也会先被第 127 行以状态/version conflict 拒绝，而不是返回已完成结果。
- 影响：网络不确定重试或 key 冲突可把课表导入永久卡死；不能保证一次外部调用、稳定 replay 或一致 failure envelope。
- 最小修复：在一个 SQLite claim 事务中同时校验 idempotency key/hash/resource、claim capability run 和 import version/status；对同 key/同 hash 返回已持久化 terminal response，对同 key/异 hash 返回 `IDEMPOTENCY_KEY_REUSED`；任何 claim 失败不改变 import。

#### P1-POLICY-001 — v0.6 capability 没有实现冻结的 Owner/day 配额和统一有界 Provider 执行

- 位置：`apps/core/src/modules/providers/capability-run-repository.ts:42-44`、`:70-74`；`apps/core/src/modules/calendar/import-service.ts:140-142`；`apps/core/src/modules/learning/service.ts:173-184`、`:325-350`；`apps/core/src/modules/learning/deepseek-learning-advice.ts:89-99`。
- 证据/复现：`claim` 只给每个 run 写 `reserved_calls=1`，从未统计/锁定同 Owner、local_date 的总 reserved/actual calls，因此可创建并执行超过每日 20 次的 runs。Vision/Search adapter await 没有统一 timeout；Search 和 Learning 都在 provider 返回完整对象后才计算 `outputChars`，DeepSeek 直接 `response.json()`，没有在解析前限制响应字节。数据库列的 check 只能拒绝最终写入，不能阻止外部费用、内存增长或挂起。
- 影响：真实 adapter 一旦配置，攻击或失控供应商可绕过每日费用上限、长期占用请求、返回超大响应造成资源耗尽；这直接违反冻结 `CAPABILITY_POLICY_V1`。
- 最小修复：实现单一事务内 Owner/day quota reservation；统一 adapter executor 强制 header/total timeout、最大输入/响应字节和 terminal lease token；在读取/解析前截断并 fail closed，所有 terminal 路径结算 reservation/actual_calls/evidence。

#### P1-EVIDENCE-001 — stale TEST_FAKE failure 会错误保留 `AUTOMATED_FAKE`

- 位置：`apps/core/src/modules/providers/capabilities.ts:55-66`；`apps/core/src/modules/providers/capability-run-repository.ts:29-32`、`:55-60`。
- 证据/复现：TEST_FAKE descriptor 在执行前即标记 `evidenceKind='AUTOMATED_FAKE'`，create 时持久化。`sweepExpired` 将过期 `RUNNING` 改为 `FAILED`，但没有把 `evidence_kind` 重置为 `NONE`。因此 stale terminal failure 会对外声称存在 Fake 成功证据，违反“所有失败为 NONE”。
- 影响：capability evidence 不再可信，失败可能被 UI/审计误读为自动成功证据；也破坏真实/模拟证据隔离规则。
- 最小修复：初始及 RUNNING evidence 一律 `NONE`；只有同一 lease 的 terminal success 才写 `terminalEvidenceKind`；所有失败和 stale sweep 明确写 `evidence_kind='NONE'`。

#### P1-ARTIFACT-001 — 畸形 WebP 容器可绕过上传前结构校验并被持久化/外发

- 位置：`apps/core/src/modules/calendar/image-metadata.ts:57-79`，尤其 `:58-62`。
- 证据/复现：解析器只检查 `RIFF`、`WEBP`、`VP8X/VP8/VP8L` 标记和固定偏移，不校验 RIFF 声明总长度、chunk 长度、padding 或 chunk 是否容纳读取字段。构造 30-byte `RIFF....WEBPVP8X`，将 RIFF/chunk size 置为 0、在 24–29 偏移放入非零尺寸，即可返回合法 dimensions，而不是 `IMAGE_DIMENSIONS_INVALID`；随后 upload service 会写 artifact。
- 影响：安全本地 artifact 边界接受损坏/伪造图片，并可能把它发送给未来 Vision adapter；冻结 probe 要求此类文件在持久化和 Provider 前拒绝。
- 最小修复：完整校验 RIFF declared size 与实际长度、首个图像 chunk size/padding 和各格式最小 payload，再读取尺寸；增加畸形 VP8X/VP8/VP8L 回归测试并断言零持久化/零调用。

### P2

#### P2-LEARNING-ERROR-001 — production DeepSeek 的严格 schema 失败被误报为 Provider unavailable

- 位置：`apps/core/src/modules/learning/deepseek-learning-advice.ts:99-105`；`apps/core/src/modules/learning/service.ts:345-353`。
- 证据/复现：adapter 第 99 行用 Zod `parse`；ZodError 不属于 `DeepSeekLearningAdviceError`，被第 105 行统一改成 `LEARNING_PROVIDER_UNAVAILABLE`。service 因此在第 345–347 行返回 503，而不会走第 350–353 行的 `LEARNING_ADVICE_INVALID` 422。注入的 raw fake 可以覆盖 422 分支，但 production adapter 的同类无效 JSON 不能。
- 影响：仍会 fail closed，不会生成 Proposal，但错误分类、重试策略和运维诊断不准确。
- 最小修复：adapter 使用 `safeParse` 并把严格输出错误映射为 `DeepSeekLearningAdviceError('LEARNING_ADVICE_INVALID')`；service 保留其 code，按 422 terminalize。

#### P2-AUDIT-001 — migration 声明的 artifact/import 审计事件没有在主要写路径落地

- 位置：`apps/core/src/storage/migrations.ts:1100-1113` 附近的 `audit_events`/event type 定义；`apps/core/src/modules/calendar/import-service.ts:61-116`、`:123-178`、`:180-215`。

#### P2-REVISION-001 — Owner revision 可静默删除 parent candidates，破坏“逐候选 included/excluded”谱系

- 位置：`apps/core/src/modules/calendar/import-service.ts:161-175`。
- 证据/复现：代码只遍历请求中的 candidates 并确认每个 id 存在于 parent；没有要求 candidateId 唯一，也没有要求请求集合与 parent 集合完全相等。提交 parent 的真子集会成功创建新 revision，被遗漏候选不是 `included=false`，而是从不可变历史的下一版静默消失。
- 影响：Owner review lineage 无法区分明确排除与请求丢项；后续 confirm 只看残余集合，可能创建不完整课表而没有告警。
- 最小修复：要求 candidateId 集合与 parent 完全相等且无重复；删除语义只能通过 `included=false` 表达。
