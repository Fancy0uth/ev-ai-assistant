### P1-REL-001：generate 业务终态与 idempotency snapshot 存在可复现 split-brain

精确位置：

- `apps/core/src/routes/daily-planning.ts:243-268`：先 `await generateApprovedPreflight`，后单独 `idempotencyService.complete`；
- `apps/core/src/modules/daily-planning/service.ts:255-275`：先提交业务终态，再单独 finish provider log；
- `apps/core/src/modules/daily-planning/repository.ts:980-1063`：事务只覆盖 Proposal insert、Run `SUCCEEDED`、preflight `CONSUMED`，不含 idempotency snapshot。

复现：在 service 返回成功后、route `complete` 前模拟 crash/fault。数据库已有 Proposal、成功 Run 和 consumed preflight，idempotency 仍为 attempt 1 `IN_PROGRESS`；lease 过期后同 key 被当成 attempt 2，但 preflight 已 consumed，只能得到 409/503，无法重放首次 201。若 `complete` 因旧 token 失败，route 甚至直接回 503，而已提交 Proposal 不会回滚。

风险：已付费 Provider 成功和业务写入无法与客户端可重放结果建立唯一事实；crash、进程退出或 fault 会制造“成功数据 + 失败响应”，违反冻结的 post-provider 短事务与 replay 语义。

最小修复边界：保留 Provider/DPAPI 网络在事务外；增加一个共享 SQLite post-provider unit of work，按 `owner_id + idempotency_record_id + current lease_token` 在**同一短事务**中完成 provider log terminal、Proposal/Run/preflight terminal 和安全 HTTP response snapshot。失败路径也应原子终结相关状态。事务前可构造/校验安全 body；事务 CAS 失败不得留下部分成功。新增 fault injection 必须分别在 Proposal、Run/preflight、provider log、idempotency snapshot 末写处证明全有或全无，并证明 crash 后 same key 能得到原 201。

### P1-REL-002：Daily Plan schedule-drift decision 返回 STALE，但外层事务把 STALE 回滚

精确位置：

- `apps/core/src/modules/daily-planning/repository.ts:1183-1218`：检测 schedule version drift 后把 Proposal 更新为 STALE 并返回 stale review；
- `apps/core/src/modules/daily-planning/repository.ts:1350-1358`：嵌套 transaction 返回后抛 `DailyPlanReviewBaseVersionStaleError`；
- `apps/core/src/routes/daily-planning.ts:359-379`：该错误在 `executeLocal` callback 内被改抛 `ApiError`；
- `apps/core/src/modules/providers/idempotency-service.ts:222-231`：异常穿出 outer transaction，回滚 business write、claim 和 snapshot。

复现：现有 schedule-drift route case 返回 409，body 中 `currentReview=STALE/version 2`；同请求后 GET Proposal 却是 `PENDING_REVIEW/version 1`。最小 mutation 的真实失败 diff 已在 §6.2 记录。

风险：HTTP 响应和持久状态自相矛盾；刷新后 Owner 又看到可操作 proposal，且同 key 没有保存该 409，违反 decision 的 claim + version/state write + response snapshot 同事务要求。

最小修复边界：repository/service 对“持久化 STALE”返回 discriminated result，不在写入后抛异常；`executeLocal` callback 将其转换成安全的 `{status:409, body}` 正常返回，使 STALE 更新与 409 snapshot 在同一外层事务提交。对其他需要稳定 replay 的 deterministic 4xx 采用同一 safe-result 边界。新增测试必须在 409 后重新 GET，并用 same key 验证完全相同 409 replay。

### P1-QUOTA-001：quota check/reservation 非原子，且错误使用计划目标日期

精确位置：

- `apps/core/src/modules/daily-planning/service.ts:202-212`：先按 `claimed.preflight.localDate` 读取 usage；
- `apps/core/src/modules/daily-planning/service.ts:213-228`：进入解密 Key callback 后才插入 STARTED 并调用网络；
- `apps/core/src/modules/daily-planning/service.ts:232-237`：token 超额只在付费响应返回后判断；
- `apps/core/src/modules/providers/reliability-repository.ts:189-192,260-274`：usage query 和 STARTED insert 是分离语句，STARTED 的 token fields 为 null，`local_date` 由调用方传入 target date。

复现 A：已有 19 attempts 时两个并发请求都读到 19，各自通过，随后 count=21。复现 B：同一实际执行日在 20 个不同 target `localDate` 上发起调用，每个日期桶都可从 0 开始；即使 Owner 当前日已到上限，另选未来/过去计划日期仍可继续付费。Asia/Shanghai 23:59→00:00 的调用日切换也没有被 clock 决定，而被 target date 决定。STARTED 的 null tokens 还使并发 token 预算没有 reservation。

风险：20 calls/100k tokens 是付费与滥用边界；当前可在网络前绕过，且事后 token check 不能撤销已产生的费用。

最小修复边界：从注入 clock 按 Owner 时区（当前单 Owner 产品为 Asia/Shanghai）计算独立 `usageLocalDate`，不得复用 plan target date；在一个 SQLite immediate/等价串行短事务中原子检查 call/token 额度并插入 attempt reservation，然后才解密 Key/发网络。reservation 必须占用可证明的保守 token budget，terminal 时以 allowlisted actual usage 对账；拒绝不能留下可调用网络的状态。加入 19→21 并发、99k token 并发、不同 target 同调用日、Shanghai 日界线和“quota reject provider call count=0”测试。

### P1-RECOVERY-001：restart 与 attempt 2 过期会留下永久 GENERATING/CLAIMED

精确位置：

- `apps/core/src/app.ts:77-222`：startup 只 compose services/routes，没有过期 lease scan/recovery；
- `apps/core/src/modules/providers/idempotency-service.ts:160-191`：attempt 1 可由同 key 接管；attempt 2 过期只 fail idempotency row；
- `apps/core/src/modules/daily-planning/repository.ts:931-978,1065-1112`：有同-key recover/fail transaction，但没有 startup 调用，也没有由第二次过期路径同步调用。

复现：attempt 2 过期后同 key 得到稳定 503，然而 Run 仍 `GENERATING`、preflight 仍 `CLAIMED`；另一个 attempt 1 crash 后关闭/reopen `buildApp`，三张表状态原样残留。浏览器刷新会丢失内存 idempotency key，因而同-key recovery 也不会发生。

风险：运行态永久残留，Today/UI/后续操作看到不可能自动终结的状态；同时 STARTED provider log 也可悬空，违反至多一次恢复与确定终态出口。

最小修复边界：Core startup 在接受请求前执行 owner/token/correlation-scoped 的过期状态 sweeper；默认 **fail closed 且不得自动真实网络调用**，在单一短事务中把过期 idempotency、Run、preflight 与 STARTED log 收敛到稳定 503/FAILED/CONSUMED terminal。attempt 2 的 request-driven terminal path 必须复用同一 unit of work。若保留 attempt 1 用户触发恢复，仍须沿用批准 snapshot/hash/owner；startup 不得擅自重发 Provider。加入真实文件 DB close→reopen、丢失 key、attempt 2 expiry 与重复 startup 幂等测试。

### P1-MIGRATION-001：`app_version='0.5.0'` 被锁入 schema/type/SQL，阻断 v0.6 且违反单一事实

精确位置：

- `apps/core/src/storage/migrations.ts:967,985-986`：两处 SQLite CHECK 固定 `0.5.0`；
- `apps/core/src/modules/daily-planning/repository.ts:311`：`DailyPlanRunRow.app_version` 类型为字面量 `'0.5.0'`；
- 同文件 `:523-529,731-740`：insert/claim/recover SQL 多处硬编码 `'0.5.0'`；
- `packages/contracts/src/daily-plans.ts:735`：Run response 又以“当前 APP_VERSION literal”解析历史记录；
- 对照 `apps/core/src/modules/providers/reliability-repository.ts:260-274` 已正确从 Contracts `APP_VERSION` 写 provider log，说明当前并非单一写入事实。

复现：v18 DB 中把 `daily_plan_runs.app_version` 写为 `0.6.0`、或插入 `provider_call_logs.app_version='0.6.0'`，SQLite 均报 `CHECK constraint failed: app_version = '0.5.0'`。SQLite 不能直接 drop/alter 既有 CHECK；未来放宽 `provider_call_logs` table constraint 或 `daily_plan_runs` column constraint 都需要 table rebuild，而冻结路线要求后续迁移只加不删、不重建已有表。

风险：v0.6 无法按路线写新的 Run/log；即便只把 Contracts `APP_VERSION` 改为 0.6，旧 0.5 Run 也会被 current-literal schema 拒绝读取。该问题直接阻断下一版入口。

最小修复边界：在 v0.5 尚未获准进入用户 DB 前修正 v18：default 可保持 `0.5.0`，CHECK 改为受限 semver/非空历史版本约束而非当前版本等值；定义可读取历史值的 `appVersionSchema`，`APP_VERSION` 只表示当前 runtime/write fact；Daily Plan insert/claim/recover 全部引用同一 `APP_VERSION` 参数，删除 TS/SQL 重复字面量。migration test 必须同时保留/read 0.5 历史行并成功写/read 0.6 行，且证明 v17→v18 数据无损。不要把修复推迟为需要 rebuild 的 v19。

### P2-WEB-001：两个通用 Proposal decision UI 路径没有保留不确定重试 key

`apps/web/src/components/schedule/manual-event-proposal-panel.tsx:249-254` 和 `apps/web/src/components/today/today-dashboard.tsx:151-154` 每次调用都立即 `createIdempotencyKey()`；transport 0/502/响应解析不确定后，用户重试同一语义会生成新 key。Daily Plan generate 和 Daily Plan proposal decision 已分别保留 correlation/semantic-action key，通用 Proposal UI 与冻结规则不一致。

Core 的 proposal version CAS 通常会阻止双 Event，所以不升 P1；但用户无法获得首次响应 replay，可能只看到 version conflict。最小后续边界是按 `{proposalId, version, decision}` 缓存 key，只在得到确定 terminal response 或用户改变语义后删除，并加 uncertain transport retry test。

### P2-EVIDENCE-001：focused E2E 直接写业务对象，证据边界不符合冻结计划

`apps/web/e2e/daily-plan-review.spec.ts:89-115` 用 Core repository/SQLite 创建 TimeRequest，`:133-150` 直接创建 schedule-change Event；冻结计划只允许 gated credential marker 作为测试基础设施，要求业务对象、preflight、approve、generate、decision 走 UI/API。
