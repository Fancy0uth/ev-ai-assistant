# V3-04：Daily Plan Contracts

## 目标与边界

为 v0.3 每日 AI 排程冻结跨层 JSON 契约；本任务只新增 Contracts 和测试，不新增迁移、Repository、HTTP 路由、Web 页面、模型调用或任何日程写入。现有 `Proposal` 继续表示可执行的日程变更，不能被 Daily Plan 草案复用或修改。

## 对象与隐私界线

| 对象 | 责任 | 可否写日程 |
| --- | --- | --- |
| `DailyPlanRun` | 一次计划生成的审计状态 | 否 |
| `DailyPlanContextManifest` | 外发上下文的类别、数量、用途和发送时间 | 否 |
| `DailyPlanModelOutput` | 受严格 JSON 约束的模型建议 | 否 |
| `DailyPlanProposal` / `DailyPlanProposalItem` | 经后续确定性校验后的待审阅草案 | 否 |

Manifest 不得包含 API Key、实体 UUID、标题、健康原文、可逆标识或项目/课程内容。模型只可使用暂存引用 `TIME_REQUEST_1` 至 `TIME_REQUEST_999`；Core 在 V3-06 才能把它映射回本地 `TimeRequest`。`DailyPlanProposalItem` 中的 `timeRequestId` 仅存在于本地草案，绝不进入 Manifest 或模型输出。

## 冻结的字段

- 契约版本：`DAILY_PLAN_V1`；模型输出版本：`DAILY_PLAN_MODEL_V1`。
- Run trigger：`MANUAL`、`SCHEDULED_0700`、`FIRST_VISIT_RECOVERY`。
- Run：`CREATED → CONTEXT_READY → GENERATING → SUCCEEDED | FAILED`。
- 草案：`PENDING_REVIEW`、`PARTIALLY_APPLIED`、`APPLIED`、`REJECTED`、`STALE`；V3-04 不实现状态转换。
- 草案项：`PENDING_REVIEW`、`APPLIED`、`REJECTED`、`INVALIDATED`；V3-04 只允许形成待审阅项。
- Manifest 只允许 `FIXED_EVENTS`、`CONFIRMED_SOFT_BLOCKS`、`OPEN_TIME_REQUESTS`、`RECOVERY_CONSTRAINTS`、`SCHEDULE_PREFERENCES` 五类条目，并仅记录字段类别和数量（每类最多 500）。`sentAt: null` 表示尚未外发。
- 模型输出只允许两种操作：`SCHEDULE_TIME_REQUEST`（必须具有合法开始/结束时间）和 `MARK_TIME_REQUEST_UNSCHEDULABLE`（必须为白名单原因码，且无时间段）。同一个 `contextRef` 在一次输出中只能出现一次。
- 失败码仅分类而不携带 Provider 原文：Provider 未配置/不可用、Context 无效、模型输出无效、不支持操作、未知引用、确定性校验失败、基础版本过期、Run 状态冲突、草案不可审阅。

## RED → GREEN 验收

1. 严格 Manifest 拒绝未知字段、自由文本、ID、超过数量上限与无效 `sentAt`。
2. 严格模型输出拒绝 Markdown、额外字段、未知操作、空白摘要、重复引用、无效时间和超过 24 项建议。
3. 草案项按操作强制时间/原因字段的互斥关系；版本均为正整数。
4. Run 的 `SUCCEEDED` 只能关联 Proposal，`FAILED` 必须带失败码且不能关联 Proposal。
5. 新类型不含 `CREATE_EVENT`、`CREATE_CALENDAR_RULE` 或任何可直接改写 Task/Event 的操作；旧 `proposalSchema` 行为不变。

## 明确不做

- 不调用 DeepSeek 或任何真实 API，不读取或保存密钥。
- 不创建、修改或删除 Event、Calendar Rule、Task、Action、Time Request。
- 不生成迁移、路由或 UI。
- 不处理用户确认、部分应用、冲突解决或 07:00 触发；这些从 V3-05 起逐步实现。
