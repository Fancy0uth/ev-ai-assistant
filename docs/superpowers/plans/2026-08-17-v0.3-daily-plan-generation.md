# V3-06 Daily Plan Generation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (\`- [ ]\`) syntax for tracking.

**Goal:** Generate an owner-scoped, provider-produced daily schedule proposal that is validated, persisted and exposed through a manual API, while leaving every user schedule record unchanged.

**Architecture:** The Core first snapshots a minimal planning context and a monotonically increasing owner schedule version. A provider-neutral service obtains the API key only through the existing DPAPI credential bridge, sends the safe projection to DeepSeek, validates the structured response locally, and atomically persists a pending proposal only if the schedule version is still current. The public endpoint is manual-only; no UI, cron runner, apply endpoint, or schedule mutation is included.

**Tech Stack:** TypeScript, Fastify, SQLite migrations, Zod contracts, Vitest, existing Windows DPAPI secret store, fetch-based DeepSeek adapter.

## Global Constraints

- Implement only V3-06 from \`docs/superpowers/specs/2026-08-17-v0.3-daily-plan-generation-design.md\`.
- Use \`DAILY_PLAN_V1\` and existing \`DAILY_PLAN_MODEL_V1\` contracts; do not change legacy v0.2 proposal contracts.
- Model input contains only local date, time ranges, durations, priorities, availability windows, fixed blocks and recovery enum; never IDs, titles, raw health text, API keys, or provider response bodies.
- All automated tests use an injected fake planning provider. Production sends no fake reply.
- No event, time-request, signal, or task write is allowed in this slice. Generated proposal and run records are the only planning writes.
- The proposal is saved as \`PENDING_REVIEW\`; no apply, reject, editor, UI, scheduling, OCR, calendar integration, or cron behavior is introduced.
- An unconfigured provider maps to HTTP 409 \`DAILY_PLAN_PROVIDER_NOT_CONFIGURED\`; unavailable provider maps to HTTP 503; invalid model output or failed local validation maps to HTTP 422; stale version maps to HTTP 409.
- Every code task follows RED → minimal GREEN → focused test → independent review → atomic commit. Use \`gpt-5.6-terra\` for implementation and review workers as requested by the user.

Append one idempotent migration that:

~~~sql
create table schedule_versions (
  owner_id text primary key references owners(id) on delete cascade,
  version integer not null check (version >= 1),
  updated_at text not null
);
insert into schedule_versions (owner_id, version, updated_at)
  select id, 1, strftime('%Y-%m-%dT%H:%M:%fZ','now') from owners;
create trigger schedule_versions_after_owner_insert
after insert on owners begin
  insert into schedule_versions (owner_id, version, updated_at)
  values (new.id, 1, strftime('%Y-%m-%dT%H:%M:%fZ','now'));
end;
~~~
