# V3-07 Daily Plan Review and Apply Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

**Goal:** Let an authenticated Owner generate, review, partially apply, or reject a daily AI planning proposal without allowing the Provider to write a schedule or complete a task.

**Architecture:** Existing generation remains immutable. An Owner-scoped proposal_decisions audit table records every human decision. A dedicated review service validates selected changes against the current schedule, then atomically creates only confirmed soft Events and advances the proposal state/version. The Web surface is one thin /daily-plan workspace that uses authenticated Core APIs only.

**Tech Stack:** TypeScript, Zod 4, Fastify, better-sqlite3, SQLite additive migrations, Vitest, Next.js 16, React, Lucide, Playwright.

**Spec:** docs/superpowers/specs/2026-08-18-v0.3-daily-plan-review-apply-design.md

## Global Constraints

- Implement only V3-07; do not rebuild /today, add the 07:00 scheduler, or alter Provider generation behavior.
- Owner ID comes exclusively from the authenticated session; all repository reads and writes are Owner-scoped.
- Provider, Web client, and API request bodies must never receive DPAPI plaintext, API keys, raw Provider text, raw health data, or another Owner's records.
- An accepted scheduled item creates one CONFIRMED, isHard=false Event and never completes, deletes, or changes the source Task/Action.
- Map PROJECT_AGENT to WORK_BLOCK, LEARNING_AGENT to STUDY, FITNESS_AGENT to WORKOUT, and NUTRITION_AGENT/SCHEDULE_COORDINATOR to PERSONAL. Event title comes only from the local TimeRequest.
- User-edited scheduled times require both startLocalTime and endLocalTime, preserve TimeRequest duration, stay within its availability window, and pass hard/soft collision plus 960-minute guards.
- Every decision batch is all-or-nothing in one SQLite transaction. Schedule-version drift marks the proposal STALE and creates no Event.
- Existing POST /v1/daily-plans/generate response remains exactly { data: DailyPlanProposal }; all V3-07 interfaces are additive.
- Tests use Fake Provider/Fake SecretStore and isolated EV_DATA_DIR; no real DeepSeek credential is committed or used in automated tests.
- Each implementation task is completed by a fresh gpt-5.6-terra agent with RED → GREEN tests, a fresh Terra review, any required repair, and an atomic commit.

- [ ] **Step 3: Implement strict schemas**

Use a strict discriminated decision union. APPLY permits neither time or both times; REJECT permits only an optional trimmed reason of at most 240 characters. Validate item uniqueness through superRefine. Operation-specific validation remains in the review service because request input does not know the stored item operation.

~~~ts
export const dailyPlanDecisionBatchInputSchema = z.object({
  expectedProposalVersion: positiveVersionSchema,
  decisions: z.array(dailyPlanDecisionInputSchema).min(1).max(24),
}).strict().superRefine((input, ctx) => {
  const itemIds = new Set<string>();
  for (const [index, decision] of input.decisions.entries()) {
    if (itemIds.has(decision.itemId)) {
      ctx.addIssue({ code: z.ZodIssueCode.custom, path: ['decisions', index, 'itemId'], message: '同一草案项只能决定一次' });
    }
    itemIds.add(decision.itemId);
  }
});
~~~

Define DailyPlanReview as { proposal, decisions }. Keep existing generation response unchanged. List response must use stable updatedAt descending then id ascending pagination.
