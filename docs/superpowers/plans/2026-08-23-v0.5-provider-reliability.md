# EV AI Dashboard v0.5 Provider Reliability 整版冻结计划

> 状态：FROZEN
> 整版基线：`bde8c29`
> 执行方式：一次整版规划 → 单个 Terra 连续实现 → 一次整版 Sol 最小冒烟审查
> 版本事实：本轮所有产品、API、运行记录和文档统一为 `0.5.0`

## 1. 版本目标

v0.5 只解决 Provider 调用链的可靠性、安全性和可证明性：

1. 为三个真实高影响入口提供 Owner 隔离的幂等语义。
2. 为 Provider 调用增加可恢复 lease、超时、配额、失败关闭和持久脱敏日志。
3. 保证 DeepSeek Key 只经 Owner UI → Core → Windows DPAPI，不进入 SQLite 明文、日志、命令行或 Git。
4. 修复 v0.4 遗留的 Web preflight action 语义关联缺口。
5. 明确 E2E 测试凭据 fixture 的证据边界，不把直接 SQLite 测试准备冒充生产 UI 流程。
6. 形成 Fake Provider 自动验收与真实 DeepSeek 人工验收两条互不混淆的证据链。

## 2. 非目标

本版不增加新的产品 Agent、工具调用、长期记忆、课程、健身、饮食、项目读取、移动原生端或云端服务；不重做现有 Proposal、Daily Plan 或 Provider UI；不改变单 Owner 模型；不安装依赖；不执行未获审批的网络请求；不使用真实密钥；不 push、tag、release；不扩大为完整生产压测或大规模 E2E。

preflight approve 不纳入 v0.5 幂等表。它是本地、带版本约束的上下文授权，不直接触发 Provider、Event 或其他外部副作用；继续由 Owner 隔离、`expectedPreflightVersion`、严格 action 语义关联和重复审批 `409` 保护。若未来该入口产生外部副作用，再单独纳入幂等契约。

## 5. 冻结契约

### 5.1 Idempotency HTTP 契约

三个高影响入口都必须读取 `Idempotency-Key`：

- 缺失：`400 IDEMPOTENCY_KEY_REQUIRED`。
- 格式不合法：`400 IDEMPOTENCY_KEY_INVALID`。
- 同一 Owner、operation 和 request hash 已完成：返回首次保存的相同 HTTP status 与 JSON，并附 `Idempotency-Replayed: true`。
- 同一 Key 正在有效 lease 内执行：`409 IDEMPOTENCY_IN_PROGRESS`，附 `Retry-After: 1`。
- 同一 Owner 使用同一 Key 但 operation、resource 或 request hash 不同：`409 IDEMPOTENCY_CONFLICT`。
- 不同 Owner 的相同 Key 互不关联，任何查询都必须包含 `owner_id`。

request hash 使用 SHA-256，输入为已解析请求的稳定规范化 JSON，加上 Owner、operation 和资源 ID；不得基于原始 JSON 字符串、Header 顺序或空白。Key 本身不得写入普通应用日志。

本版 operation 固定为：

- `daily_plan.generate`
- `daily_plan.proposal.decision`
- `proposal.decision`

两个本地 decision 路由必须在同一 SQLite 事务内完成：幂等 claim、既有业务版本检查/状态变更、响应快照落盘。Generate 使用短事务 claim，网络调用在事务外执行，再用 lease token 在短事务内完成；不得持有数据库事务等待网络。

### 5.2 DeepSeek 配置与响应白名单

以下为本版冻结的配置/白名单事实：

- endpoint：`https://api.deepseek.com/chat/completions`
- 允许模型：`deepseek-v4-flash`、`deepseek-v4-pro`
- 禁止模型：`deepseek-chat`、`deepseek-reasoner` 以及任何不在白名单中的值
- 请求为非流式
- 允许持久化的 usage 顶层字段仅为：
  - `prompt_tokens`
  - `completion_tokens`
  - `total_tokens`
- cache/reasoning 细分即使响应存在，本版默认不持久化；如实现必须显式逐字段加入常量白名单，禁止保存任意 JSON。
- 允许的 `finish_reason`：
  - `stop`
  - `length`
  - `content_filter`
  - `tool_calls`
  - `insufficient_system_resource`
- 未知 finish reason 映射为本地 `unknown`，原值不落盘。
- 提示词、回复正文、原始响应、HTTP body、Authorization 和 API Key 均不得进入持久日志。

`length`、`content_filter`、`insufficient_system_resource`、未知/畸形响应必须按失败关闭处理；`tool_calls` 在 v0.5 没有工具执行器，也必须失败关闭，不能伪造成已生成计划。

### 5.3 Provider 安全与运行策略

- 真实 Key 仅允许 Owner 在设置页输入，经 BFF 传给 Core 后立即交给 DPAPI；SQLite 仅保存现有密钥引用和非敏感元数据。
- UI、Core 响应、日志、异常、测试快照和 shell 命令均不得回显真实 Key。
- 生产配置拒绝 Fake Provider。Fake 只允许测试依赖注入，且必须由测试进程显式构造，不能通过生产环境变量选择。
- 未配置：`503 AGENT_PROVIDER_NOT_CONFIGURED` 或现有等价 Provider 未配置错误；不得写入伪造成功消息或计划。
- Provider 不可用、超时、配额耗尽、响应不合法均 fail closed，并保留可诊断的脱敏原因。
- 默认策略集中定义，测试可覆盖：
  - headers timeout：5 秒
  - total timeout：15 秒
  - lease：20 秒
  - 单次输入/输出字符上限：各 20,000
  - 单次 run 最大 Provider 调用：2
  - Owner 本地日调用上限：20
  - Owner 本地日 token 上限：100,000
  - completion token 上限：2,000
- 配额按 Owner 与本地自然日计算；只统计已发起的真实/Fake Provider attempt。拒绝发生在网络调用之前，并返回稳定错误码。
- HTTP abort、超时、进程退出和晚到响应都不能绕过 lease token 校验。

## 7. Lease、恢复与并发

Generate 状态机：

1. 短事务创建/读取 idempotency record，并原子 claim attempt 1。
2. 写入随机 lease token、20 秒到期时间和 deadline。
3. 事务外调用 Provider。
4. 仅当前 lease token 可完成 run、日志和 idempotency 响应快照。
5. 旧 token 的晚到响应必须被拒绝，不能覆盖新结果。
6. 启动恢复或同 Key 后续请求发现 attempt 1 lease 已过期时，可原子恢复一次为 attempt 2。
7. attempt 2 再过期后终结为 `INTERRUPTED`/稳定 503，并封存 idempotency 结果；不得无限重试。
8. 恢复必须沿用同一 Owner、operation、request hash、已批准输入快照和 idempotency record。
9. 生产恢复只针对用户此前已授权的原操作；开发与自动验收只注入 Fake，不产生真实网络。
10. 并发测试必须覆盖：双请求只有一个 Provider 调用、完成重放、payload 冲突、lease 过期接管、晚到响应拒绝、第二次过期终结。

## 8. v0.4 P2 闭环

### Web preflight action semantic correlation

`use-daily-plan-preflight.ts` 不得只检查 HTTP/schema 成功。prepare 返回的 action/intent 标识、approve 请求和 generate 请求必须形成同一语义关联；任何 action、proposal、version 或 payload 指纹不一致都在浏览器端停止，并在 Core 继续执行权威校验。不得仅依赖按钮当前状态。

### E2E credential fixture 证据边界

`daily-plan-test-bootstrap.ts` 可继续直接写入独立测试 SQLite 的假凭据 marker，但必须：

- 只在隔离 `EV_DATA_DIR` 和测试进程启用。
- marker 不具备真实 Key 形态，不经过网络。
- 测试报告明确：“凭据准备为测试基础设施证据，不证明 Owner UI → Core → DPAPI 的生产流程。”
- 业务对象、preflight、approve、generate、decision 仍通过 UI/API 真实路径产生。
- 另以单元/集成测试证明 credential-service 调用 DPAPI port、响应与日志不泄密；真实 DPAPI/DeepSeek 验收保留为人工审批项。

## 11. 停止边界、回滚与最终审查

立即停止并交回主 Agent的情形：

- 需要新增外部服务、依赖、真实凭据或网络调用。
- 需要破坏性迁移、重建已有表、清除用户数据或修改单 Owner 边界。
- 需要改变已冻结 endpoint/模型事实或引入工具执行。
- 聚焦验证发现必须扩张到 v0.6+ 产品范围才能解决的问题。
- 发现 Key、正文或 Authorization 已进入 Git/SQLite/日志。

回滚以内部原子提交为单位，逆序 revert H→A；v18 是纯加法迁移，不自动向下删除表/列。若迁移后回滚应用，旧 v17 代码必须忽略新增表/列；禁止自动删除用户数据。

整版完成后只进行一次新上下文 Sol 最小冒烟审查，输出：

`docs/reviews/2026-08-23-v0.5-sol-smoke-review.md`

## 12. 残余审批门

v0.5 唯一预留的外部审批门是：是否允许使用用户通过 Owner UI 提供的真实 DeepSeek Key 进行一次最小人工验收。在获得明确批准前：

- 不执行真实 DeepSeek 请求；
- 不把 Key 写入命令、测试 fixture、SQLite、日志或 Git；
- 真实外部证据保持 `NOT RUN — APPROVAL REQUIRED`；
- Terra 仍可依靠 Fake Provider、契约测试和 DPAPI port 测试完成全部工程实现与自动验收。
