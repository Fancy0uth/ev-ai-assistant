# V3-06：可校验 Daily Plan Proposal 设计

## 目标

把 V3-05 的本地 planning packet 转化为一份 `PENDING_REVIEW` 的每日计划草案：Provider 只能返回 V3-04 已冻结的严格 JSON；Core 必须校验引用、时间、硬日程冲突、负荷与日程版本，再原子保存草案。任何失败都不改写 Event、Task、Action 或 TimeRequest。

## 范围与非目标

- 包含：可替换 DailyPlanningProvider Port、DeepSeek 生产 adapter、自动化测试用 Fake、确定性校验、草案持久化、认证的手动生成 API。
- 不包含：草案编辑、确认/拒绝、任何日程写入、Today UI、07:00 调度、外部搜索、项目/课程/健身专用 Agent。
- 自动化测试一律注入 Fake Provider；真实 DeepSeek 只在 Owner 已配置凭据、主动触发生成时调用。

## A：保守日程版本保护

新增每个 Owner 一行的 `schedule_versions`，初始版本为 1。SQLite 触发器在下列本地数据变化时递增版本：

- 任意 Event 插入、更新或删除；
- 任意 TimeRequest 插入、更新或删除；
- `RECOVERY` Signal 插入、更新或删除。

其他 Signal 不影响排程版本。该版本按 Owner 全局递增，而非按日期递增：跨日期变动也会保守地让草案失效。Context packet 读取当前版本；Provider 返回后、草案保存前必须再次读取。版本不一致时 Run 标为 `FAILED / DAILY_PLAN_BASE_VERSION_STALE`，不创建 Proposal。

## Provider 与数据边界

`DailyPlanningProvider.generate(input)` 是唯一的模型 Port。生产 adapter 从 `ProviderCredentialService.withApiKey` 的 callback 中短暂取得 Key，并调用 DeepSeek Chat Completions；Key 不进入 packet、日志、数据库或 API 响应。

发送的 provider input 只含：日期、硬/软时间块的时间范围和硬性标记、`TIME_REQUEST_n`、时长、优先级、可用窗口、固定性与枚举 Recovery Level。它不含本地 UUID、任务/事件标题、原始健康数值、记忆、课程/项目内容或 API Key。真实调用必须显式由 Owner 的 `POST /v1/daily-plans/generate` 触发；无凭据或 Provider 不可用不会产生草案。

## 确定性校验

模型输出先用 `dailyPlanModelOutputSchema` 解析，再按下列规则校验：

1. 每个 `contextRef` 必须来自本次 packet，且只能出现一次。
2. `SCHEDULE_TIME_REQUEST` 的时长必须等于对应请求的 `durationMinutes`；开始/结束须位于 05:00–23:00，且满足可用窗口。
3. 排程项不得与硬时间块或另一排程项重叠。
4. 每日总排程时长不得超过 960 分钟。
5. `MARK_TIME_REQUEST_UNSCHEDULABLE` 的原因码必须由冻结 schema 接受。
6. 任一校验失败仅把 Run 标为 `FAILED / DAILY_PLAN_VALIDATION_FAILED`，不保存 Proposal。

软时间块会发送给模型供取舍，但本轮不作为确定性拒绝条件；用户将在后续审阅界面看到取舍。

## 持久化与原子性

Migration 14 新增：

- `schedule_versions`：`owner_id` 主键、正整数 `version`、`updated_at`；为已有 Owner 回填，且在新 Owner 创建时创建初始行。
- 上述版本触发器。
- `daily_plan_proposals`：Owner、Run、契约版本、日期、状态、`base_schedule_version`、摘要、严格 JSON `items_json`、版本及时间戳；Run 使用外键，Owner/date/status 索引支持后续读取。

在一个 SQLite transaction 中，服务必须：重新校验 schedule version、写入 `daily_plan_proposals`、将对应 `daily_plan_runs` 从 `CONTEXT_READY` 更新为 `SUCCEEDED` 并填入 Proposal ID/完成时间。失败路径只更新该 Run 为 `FAILED` 并写分类失败码；任何表中都不保存 Provider 原文。

## API

新增严格输入 `{ localDate: ISO date }` 的 `POST /v1/daily-plans/generate`。认证失败为 401；输入非法为既有 422 结构；未配置凭据为 `409 DAILY_PLAN_PROVIDER_NOT_CONFIGURED`；Provider 不可用为 503；模型输出或确定性校验失败为 422；版本变动为 409。成功响应为 `{ data: DailyPlanProposal }`，状态 201。

## 测试与验收

1. Migration 12 升级后保留 Owner、Task 与 Provider 行，并得到 Migration 14 表/触发器。
2. Event、TimeRequest、Recovery 变化使版本递增；其他 Signal 不递增。
3. Fake Provider 合法输出产生 `PENDING_REVIEW` Proposal 与 `SUCCEEDED` Run；没有任何日程实体被写入。
4. 硬日程冲突、窗口越界、时长不符、重复/未知引用、超负荷及版本变动均不产生草案。
5. Run/Proposal Owner 隔离；失败分类不含请求正文、Key 或 Provider 原文。
6. HTTP 路由的认证、未配置 Provider、成功生成及错误码全部有 Fastify 集成测试。

## 分解

2. **V3-06b — Provider 与生成 API**：Provider Port/DeepSeek adapter、Planning Service、路由/App 注入、Fake Provider 集成测试。
