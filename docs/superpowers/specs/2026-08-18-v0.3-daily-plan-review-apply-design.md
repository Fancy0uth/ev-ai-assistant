# V3-07 每日计划草案审阅与确认设计

**状态：** 待用户审阅

**日期：** 2026-08-18

**前置：** V3-04 至 V3-06（Provider、脱敏 Context、草案生成与本地校验）
**后续：** V3-08 Today 日程优先重构、V3-09 Context/Plan Review 产品化

## 1. 目标

把 `PENDING_REVIEW` 的每日计划草案变成一个由 Owner 主动控制的闭环：在最小审阅页中生成、查看、逐项调整、部分采用或拒绝建议。采用一个可排程建议时，只创建可编辑的软性日历时间块；源 `TimeRequest` 和其对应的原任务不会被完成、删除或改写为完成。

这是 proposal-only 原则第一次允许日程写入，但写入只能由已认证 Owner 的明确确认触发。Provider 没有日程写接口、不能自动确认，也不能写任务或外部系统。

## 2. 范围与非目标

### 本切片包含

- Owner 范围内的草案读取、逐项决定、审计记录、部分采用、拒绝和过期处理。
- 对 `SCHEDULE_TIME_REQUEST` 项目，允许仅调整开始与结束时间；时长保持与原 TimeRequest 一致。
- 每次确认使用一个 SQLite 事务：验证版本、验证选中项、创建所有软性 Event、记录决定、更新草案状态；任何一步失败即全部回滚。
- 一页最小可用的 `/daily-plan` 审阅界面：日期、显式“生成草案”、Provider 未配置提示、草案列表、时间编辑、采用/拒绝和刷新后的状态。
- 回归测试覆盖 Owner 隔离、事务性、版本冲突、重复提交、编辑后再校验和浏览器中的关键操作。

### 明确不包含

- Today 首页的完整时间轴重构、Context 解释面板、提醒、07:00 自动触发、首次访问补偿。
- 草案整体一键接受、草案删除、撤销已采用项目、重新打开已拒绝项目或手动新建 TimeRequest。
- 修改任务完成状态、创建/修改硬性 Event、外部日历写入、OCR、长期记忆、真实 API 凭据的自动化测试。
- 自动重排、Provider 再调用、项目/课程/健身专用 Agent。

## 3. 用户行为与状态机

### 3.1 逐项决定

草案项的初始状态为 `PENDING_REVIEW`。用户可只提交其中一部分决定；未提交的项保持待审阅。

| 草案项类型 | 用户操作 | 结果 |
| --- | --- | --- |
| `SCHEDULE_TIME_REQUEST` | 采用 | 创建一个 `isHard=false`、`CONFIRMED` 的 Event；Event 标题只取本地 TimeRequest 标题，任务状态不变；项变为 `APPLIED`。 |
| `SCHEDULE_TIME_REQUEST` | 修改时间后采用 | 用用户提供的时间创建 Event；仍必须通过相同的本地规则校验；项变为 `APPLIED`。 |
| 两种项 | 拒绝 | 不写入 Event；项变为 `REJECTED`，可保存至多 240 字的拒绝理由。 |
| `MARK_TIME_REQUEST_UNSCHEDULABLE` | 采用 | 记录“接受无可用时段”的审计决定但不创建 Event；项变为 `APPLIED`。 |

`SCHEDULE_TIME_REQUEST` 的修改必须同时给出开始和结束时间、保持原 TimeRequest 的分钟数，并落在该请求的可用窗口内。修改后的项还必须不与硬 Event、已确认软 Event 或同批新 Event 冲突，且当天总计划量不超过 960 分钟。

### 3.2 Proposal 状态

- 有任何 `APPLIED` 项且仍有 `PENDING_REVIEW` 项：`PARTIALLY_APPLIED`。
- 所有项均已处理且至少一项为 `APPLIED`：`APPLIED`。
- 所有项均为 `REJECTED`：`REJECTED`。
- 只拒绝一部分而没有采用项：Proposal 保持 `PENDING_REVIEW`。
- 生成后的基础日程版本不再匹配：Proposal 变为 `STALE`；所有仍待审阅项保持原状态但不可再采用。

项目一旦 `APPLIED` 或 `REJECTED` 即为终态；重复提交或再次决定它会被拒绝，客户端刷新最新草案，而不是猜测结果。

### 3.3 已处理请求不会被重复安排

新增只读审计表 `proposal_decisions`，每个 `(proposal_id, proposal_item_id)` 只能有一条决定。它记录本地 `time_request_id`、决定、可选 Event、实际时间及可选拒绝理由。

每日计划 Context 查询将排除已经存在“已采用决定”的 TimeRequest：

- 已安排项由关联的、仍 `CONFIRMED` 的 Event 表示已占用；若 Event 被取消或删除，该请求会重新进入后续排程 Context。
- 已接受“无可用时段”项在它的目标日不再重复进入同日草案；源任务仍独立保留，用户可在后续迭代中手动新建新的时间请求。

这样既防止同一请求被多份草案反复放进日历，也不把“已安排”误写成“任务已完成”。

## 4. 一致性、冲突与事务

草案带有 `baseScheduleVersion`。确认前，服务在单个 SQLite 事务内执行：

1. 读取 Proposal、其当前版本和 Owner 当前 `schedule_versions.version`。
2. 验证 Owner、`expectedProposalVersion`、项目状态、TimeRequest 版本以及决定输入。
3. 若当前日程版本不等于草案基础版本，将 Proposal 标记为 `STALE`，不创建 Event，返回冲突。
4. 对所有待采用时间项使用当前日程做确定性重校验；然后创建 Event 与决定记录，并更新草案 JSON 中的项目状态/实际时间。
5. SQLite 触发器使新 Event 递增日程版本。服务将 Proposal 的 `baseScheduleVersion` 更新为这次写入后的版本，以支持同一草案之后继续部分确认。
6. 计算新的 Proposal 状态、递增 Proposal 版本并提交。

一次请求中的所有选择要么同时保存，要么完全不保存。冲突、请求过期、未知项目、重复项目、已处理项目或本地时间规则失败都不会产生半份日程。

## 5. Core 模块边界

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| Contracts | 严格定义 Review、Decision、列表、错误与输入/输出 schema | 数据库和业务写入 |
| DailyPlanningRepository | Owner 范围查询、Proposal/Decision/Event 的原子持久化、版本更新 | HTTP 解析、Provider 调用 |
| DailyPlanReviewService | 项目选择、编辑后本地校验、状态转换、冲突映射 | 直接访问 Web 或密钥 |
| Calendar Repository | 创建标准软 Event，维持现有时间轴语义 | 理解 AI 输出 |
| Daily planning Context builder | 排除已采用的请求，维持最小化/脱敏 Provider packet | 泄露标题、UUID 或健康原文给 Provider |
| Web `/daily-plan` | 展示状态、显式提交决定、渲染准确错误与键盘/触摸操作 | 访问 DPAPI、直接写 SQLite 或伪造 Provider 结果 |

## 6. HTTP 与 Contracts

所有端点先执行认证，再验证输入；错误沿用 `{ error: { code, message, details? } }` 包装。Owner ID 永远从会话得到，客户端不可传入。

| 方法与路径 | 请求 | 成功 | 用途 |
| --- | --- | --- | --- |
| `GET /v1/daily-plans/proposals?localDate=YYYY-MM-DD&page=1&pageSize=20` | 严格日期和分页查询 | `200 { data, pagination }` | 恢复某天的草案列表；按最近更新排序。 |
| `GET /v1/daily-plans/proposals/:proposalId` | UUID path | `200 { data: DailyPlanReview }` | 读取草案及已保存决定。 |
| `POST /v1/daily-plans/proposals/:proposalId/decisions` | `{ expectedProposalVersion, decisions[] }` | `200 { data: DailyPlanReview }` | 原子提交一批采用/拒绝决定。 |

`decisions` 至少一项、至多 24 项，`itemId` 必须唯一。每项是严格的判别联合：

- `APPLY`：对于排程项可省略时间以采用原建议，或同时给出 `startLocalTime/endLocalTime`；对于无可用时段项不得给出时间。
- `REJECT`：不得给出时间，可选非空且至多 240 字的 `reason`。

`DailyPlanReview` 是新的读取资源，形如 `{ proposal, decisions }`；它不改变已存在的生成响应 `{ data: DailyPlanProposal }`，因此为加法接口。`decisions` 只公开项状态、实际采用时间、拒绝理由和关联 Event ID；不公开 Provider 原文或密钥。

| 条件 | HTTP | 错误码 |
| --- | ---: | --- |
| 未认证（包括非法 body） | 401 | `AUTHENTICATION_REQUIRED` |
| 输入、query、UUID 或时间编辑不符合 schema | 422 | `VALIDATION_ERROR` |
| 草案不存在或不属于当前 Owner | 404 | `DAILY_PLAN_PROPOSAL_NOT_FOUND` |
| `expectedProposalVersion` 已过期，或项目已处理 | 409 | `DAILY_PLAN_PROPOSAL_VERSION_CONFLICT` |
| 基础日程已变化，草案被标记为过期 | 409 | `DAILY_PLAN_BASE_VERSION_STALE` |
| 本地时间/冲突/时长校验失败 | 422 | `DAILY_PLAN_VALIDATION_FAILED` |

冲突响应会携带当前 `DailyPlanReview`，使 Web 能刷新而不静默覆盖用户界面。网络重试若落到新版本同样得到该明确冲突与当前状态；客户端不得自行重放旧选择。

## 7. 最小审阅页

路径为 `/daily-plan`，纳入现有 authenticated dashboard shell 和桌面/移动导航，但不重构 `/today`。

- 顶部：日期选择、显式“生成草案”按钮、Provider 未配置时的设置入口；没有 Key 时不显示假建议。
- 草案：摘要、状态、更新时间、建议列表。可排程项显示时间输入框与时长；无可用时段项显示原因和“接受此结论”标签。
- 每项：可选择采用/拒绝；拒绝理由按需展开。提交仅发送用户已选择的待审阅项。
- 成功后重新使用服务端返回的完整 Review 刷新本地状态；冲突后显示“日程已变化，请重新生成”，禁用旧草案写入。
- 小屏以单列卡片、至少 44px 触摸目标和无横向溢出呈现；桌面保留清晰的决策和时间编辑区。

## 8. 测试与验收

### RED/GREEN 最小覆盖

1. Contracts 拒绝重复 `itemId`、半对时间、错误时长、无可用时段项带时间和拒绝项带时间。
2. Repository/Service 证明：部分采用只创建所选 Event，源 Action/Task 不变；全部拒绝不创建 Event；采用无可用时段项不创建 Event。
3. 服务证明：原草案版本冲突、日程版本冲突、TimeRequest 版本冲突、硬 Event 冲突、批内冲突全部无部分写入。
4. Context 回归：已采用排程请求不重复出现；关联 Event 被取消/删除后重新出现；已接受无可用时段请求在同日不重复出现。
5. Routes 证明：认证优先、Owner 隔离、404、422、409 和成功返回一致的 schema。
6. Web：生成入口、未配置状态、选择/编辑/采用/拒绝、冲突刷新、刷新页面后状态保留、键盘焦点和移动触摸目标。

- 无 TBD/TODO 或待定接口；所有状态、写入对象和失败语义均已明确。
