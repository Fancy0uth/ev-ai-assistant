## 1. MVP 的定义

本 MVP 不是「做完所有外部集成」的承诺，也不是只有静态页面的视觉原型。它的目标是让一个单一 Owner 能完成一条可信的本地每日控制闭环：

> 看到今天 → 了解每项安排的来源与原因 → 进入对应模块处理 → 接受或拒绝 Agent 建议 → 将确认后的安排放回今天的日程 → 留下可追溯的本地记录。

因此，MVP 必须覆盖工作项目、课程学习、健身恢复、饮食身体和日程协调这些用户可见的领域；但每个领域只实现一条最小、端到端、可验证的真实业务链路。广泛的外部平台集成、更多数据源和自动化由后续迭代承担。

## 2. MVP 成功标准

当用户在本地电脑或 iPhone 浏览器打开 Dashboard 时，应能完成以下体验：

1. 立刻看到今天的时间线、固定课程/事件、具体行动、恢复 Signal 与待处理 Proposal。
2. 点开一件事项，进入它所属的项目、课程、训练或饮食详情，而不是通用待办列表。
3. 让任意领域 Agent 提出一个结构化建议或时间请求；日程协调器展示冲突、理由与取舍；用户确认后日程才更新。
4. 录入一次睡眠/精力/不适或饮食反馈，并在当日计划/统计中看见相应结果。
5. 对一个授权的本地项目得到只读 Project Brief；整个过程中没有项目文件或 Git 写入。
6. 查看、修正或删除至少一条分域本地记忆；没有未解释的云端同步。
7. 在设置页配置一个模型 Provider，或在未配置时得到清楚的不可用说明而非伪造回复。

## 3. MVP 范围

### 3.1 共同底座

| 能力 | MVP 最小闭环 | 不在本轮扩展 |
| --- | --- | --- |
| 单 Owner 本地账户 | 创建唯一 Owner、登录、退出、真实错误提示 | 多用户、邀请、密码找回 |
| 本地数据 | 日程、模块记录、Proposal、记忆与设置仅存本地 | 云同步、多设备冲突合并 |
| Provider 设置 | 一个可替换的模型 Provider 配置入口、连通性/未配置状态 | Provider 市场、自动模型路由、多 Provider 编排 |
| 响应式 Web | 桌面和 iPhone 浏览器可完成核心流程 | 原生 iOS/Android App |
| Proposal 框架 | 生成、查看依据、编辑、确认、拒绝、审计 | 无人确认的外部写入 |

### 3.2 Today Control Console

首页必须同时提供「日程」与「具体可执行事项」的视图。最小闭环包括：

- 今日日期、当前时间、恢复 Signal 摘要；
- 以时间块呈现的 Event、Session 与 Action；
- 带所属模块、状态、优先级和预计时长的行动列表；
- 昨日完成度/学习完成度的可量化占位或真实聚合；
- 待确认 Proposal 的清晰入口；
- 从首页到所有模块详情页的真实路由跳转。

首页不以常驻聊天为中心；聊天/Agent 是辅助入口。没有可用数据时应展示真实的空状态与下一步，而不是伪造今天的计划。

### 3.3 日程、课程与每日协调

| 能力 | MVP 最小闭环 |
| --- | --- |
| 日程对象 | Event、Action、Session、Signal 和硬/软时间块能够关联到具体日期 |
| 课表输入 | 用户可提交一张课表截图；系统展示带不确定字段的课程/重复规则候选 Proposal；确认后形成课程与日程实例 |
| 自然语言事项 | 用户可描述会议、约会等事项，得到候选 Event、冲突和影响说明，确认后写入 |
| 每日协调 | 本地 07:00 生成当日调整 Proposal；当天首次访问可触发简短 Check-in；未确认不改变日程 |
| 冲突处理 | 依据硬 Event → 健康限制 → 截止日期 → 课程预习 → 训练目标 → 习惯偏好的默认顺序解释排程；用户可覆盖 |

MVP 只要求一条课表识别和一条自然语言日程建议链路可用。复杂的跨学期排课、批量导入、Apple 日历双向同步和通知推送不在本轮。

### 3.4 项目工作 Agent

用户显式选择一个本地目录后，Project Agent 只能读取该目录中的代码、Git 状态/提交、PRD/技术文档、任务文档和测试结果。它必须输出包含当前阶段、已完成信号、下一步 Action、风险/依赖、预计时长和时间请求的 Project Brief。

MVP 只支持一个已授权项目目录及其只读分析。它不得写入任何项目文件，不得执行可能改变项目的命令，也不得创建分支、提交、推送或合并。多仓库组合规划、GitHub 远程协作、Issue/PR 自动化后置。

### 3.5 课程学习 Agent

每门课程有独立档案，至少包含名称、上课规则、用户提供的课程链接/大纲/材料、当前阶段与学习记录。MVP 要完成一条「临近课程 → 根据课程档案与一条公开资料检索 → 输出来源可见的预习/复习 Action 和时间请求 → 用户确认」的链路。

自动登录学校系统、抓取受保护内容、多格式文档批量解析、跨课程知识图谱和考试预测均后置。Agent 必须明确区分官方资料、用户资料、公开资料和自身推断。

### 3.6 健身与恢复 Agent

MVP 引入一套本地、带来源/版本/许可记录的动作数据。用户可维护基础目标、器械条件、限制及训练反馈，并在每日进行简短睡眠/精力/不适 Check-in。

闭环为：原始 Check-in 本地保存 → 可解释恢复因子与自由文本理解 → 恢复 Signal → 动作检索 → 训练 Session Proposal（含替代动作、时长、调整原因）→ 用户确认 → 日程协调器安排 → 用户记录完成与感受。RAG 仅用于训练资料和动作解释，不作为动作事实或医学结论来源。

MVP 不提供医学诊断、处方、可穿戴设备同步、自动动作识别、复杂周期化训练或训练计划市场。

### 3.7 饮食与身体目标 Agent

MVP 支持自然语言录入食物和数量。闭环为：模型解析候选食物/单位/数量 → 一个可替换的营养数据 Provider 查找数值 → 核心计算能量和营养素 → 用户编辑或确认 → 保存为本地饮食记录，并体现在当天的目标进度中。

系统保存已确认常见食物、用户食谱和包装食品的来源/版本快照。模型不应充当营养数值事实来源。数据 Provider 的具体供应商将在技术设计选择，并应具备适配中国食物场景的路径。

MVP 不包括照片识别、餐厅实时菜单、购物下单、医疗饮食处方、完整微量元素体系或可穿戴设备数据。

### 3.8 多 Agent、记忆与隐私

各领域 Agent 只产生结构化建议和时间请求，不能直接彼此覆盖日程。日程协调 Agent 汇总请求并产生唯一的日程 Proposal。

MVP 提供可视化的本地分域记忆入口，至少覆盖用户、日程、一个项目、一个课程、健身和饮食。用户可查看、编辑、删除、恢复版本。原始用户记录与日常摘要可静默更新；外部网页或模型推断不能自动成为高影响个人事实。

涉及健康敏感信息的外部 API 调用须展示可编辑的 context packet，提供「最小必要」与「完整上下文」选择。该控制约束外发内容，不要求用户逐条确认本地记忆更新。

## 4. 技术设计阶段内可选的交互原型

学院规定的下一步是技术方案/系统设计，而不是单独的 Demo 阶段。若在技术设计中需要验证信息架构、流程、页面层级、确认边界或跨端体验，可以制作交互原型作为辅助设计产物；它不替代 `TECH_SPEC.md`、`ARCHITECTURE.md` 的审核，也不构成进入任务拆解前的额外关卡。

如制作原型，应遵守：

1. 使用一位受控示例用户、一周课程、一个项目、一份训练计划和若干饮食记录演示闭环。
2. 截图识别、公开搜索、模型分析和营养查值如使用样例结果，必须在界面或说明中标为「示例/模拟结果」及其来源；不得伪装为实时 API 响应。
3. 原型中的确认、拒绝、改期、完成、记忆编辑和跨页面跳转可用于验证交互，但不是已实现真实后端的证据。
4. 原型应同时检查桌面与 390×844 iPhone 视图：首页、日程 Proposal、项目 Brief、课程页、训练、饮食、记忆和设置。
5. 真实实现的存储、Agent Port、Provider、数据源和权限边界必须先由技术设计定义，再由任务拆解和测试验证。

## 5. 延期项（明确不进入 MVP）

- Apple 日历导入/双向同步、Google/Outlook 日历；
- 小米手环或其他穿戴设备数据接入；
- 学校受保护网站自动登录、爬取或绕过认证；
- 原生 iOS/Android、推送提醒、公开互联网直接暴露、Tailscale/Docker 部署；
- 多用户、团队协作、云同步、公开 SaaS；
- 自动修改项目代码/Git 仓库、GitHub 写入自动化；
- 长时间自主运行且无需确认的执行 Agent；
- 医疗诊断、治疗建议、处方及紧急决策；
- 多 Provider 自动竞价/路由、复杂模型训练或微调。

## 6. MVP 验收口径

Demo 和之后的真实实现均应按以下口径验收：

| 验收类别 | 必须证明的结果 |
| --- | --- |
| 日常闭环 | 至少一条从首页到模块处理、再回到已确认日程的完整路径 |
| 安全边界 | 未确认不写日程；项目分析零写入；未配置 Provider 不伪造成功回复 |
| 数据边界 | 记忆与业务数据本地可见；外部调用只显示并发送所选 context packet |
| 领域差异 | 项目、课程、训练、饮食详情页具有不同对象与处理逻辑 |
| 可解释性 | 每个 Proposal 展示理由、来源/信号、冲突和影响 |
| 多端体验 | 桌面与 iPhone 浏览器可完成核心流程，无横向溢出，路由支持刷新/返回 |
| 质量 | 核心流程具备自动化测试；真实实现不以演示数据掩盖失败的 API 或存储行为 |
