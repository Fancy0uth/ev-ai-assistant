## 1. 背景与问题

目标用户是有编程/项目工作需求、同时需要兼顾研究生课程、训练、饮食与日常生活的人。现有待办工具擅长记录，却不能理解「今天这段时间为何要安排这件事」、任务与课程/项目/身体状态之间的关系，也难以持续跟进长期目标。

EV AI Dashboard 要成为一套本地运行的个人 AI 助手系统：以一天和时间块为组织骨架，把用户的课程、工作项目、学习、健身、饮食、恢复与生活安排汇集在同一个可操作的 Dashboard 上。AI 的职责是读取用户授权的信息、提出有依据的安排和下一步建议；用户始终保有确认、修改、撤销与查看记忆的权利。

它不是普通 To-do List，也不是打开首页就开始闲聊的「晨间 Brief」产品。首页首先必须可见地回答：今天什么时候做什么、哪些具体事项需要我处理、这些事项来自哪个模块、我为什么这样安排。

## 2. 产品目标与成功体验

### 2.1 产品目标

1. 让用户在打开首页时立即看清当天的时间线、日程与可执行事项。
2. 让每项任务属于明确的业务模块和上下文，而不是笼统的「工作任务/学习任务」分类。
3. 用受约束的多个专业 Agent 形成建议，并由统一的日程协调流程产出可确认的计划。
4. 将敏感个人数据、长期记忆、Agent Loop 与主要存储保留在用户自己的常开电脑上；仅在用户配置外部模型 API 时按最小必要原则发送上下文。
5. 同一套响应式 Web Dashboard 同时服务桌面与 iPhone 浏览器访问。iPhone 是远端控制入口，而非本期原生 App。

### 2.2 成功体验

一位用户在本地时间早上 07:00 或当天首次打开 Dashboard 后，可以在一个页面中看到：固定课程/会议、按优先级排出的工作与学习事项、当日训练/饮食动作、恢复状态，以及需要确认的 AI 建议。他点击任一事项即可进入该事项所属的项目、课程、健身或饮食页面继续处理。

当用户发来一张课表截图、描述一次约会，或授权一个本地项目目录时，系统不会直接改写日程或项目；它会解释识别/分析结果，形成结构化 Proposal，待用户确认后才写入具有外部影响的计划数据。

## 3. 用户、边界与产品原则

### 3.1 首期用户

- 单一 Owner：当前部署由一位用户拥有和使用。
- 有本地电脑、愿意配置模型 API，并希望通过 iPhone 浏览器远程查看/更新个人控制台的技术用户。
- 典型身份为计算机相关从业者或 AI 方向研究生，拥有 GitHub/本地项目、课程资料及可持续的训练和饮食目标。

### 3.2 产品原则

1. **日程优先，模块落地。** 日程与时间块是统一入口；项目、课程、训练、饮食等模块拥有各自的数据和详情逻辑。
2. **建议先于执行。** Agent 可阅读、分析、提出 Proposal；涉及日程写入、重要安排变更和外部影响的操作必须由用户确认。
3. **本地优先，最小外发。** 本地数据库、可读记忆文件和 Agent Loop 不上传云端。外部模型调用只发送可见、可编辑、满足当前问题的上下文包。
4. **专业分工，不自由失控。** 各领域 Agent 只在自己的职责内工作；日程协调器统一处理时间冲突。
5. **记忆默认自动维护，但可追溯、可纠正。** 不把每一次记忆更新都变成用户审批负担；用户仍可随时查看、编辑、删除和恢复。
6. **人类拥有最终决定权。** 用户可覆盖优先级、拒绝建议、修订事实和手动完成里程碑。
7. **不假装已连接。** 未配置模型、数据源或外部服务时，界面必须明确说明能力不可用，而不能伪造 AI 回复或真实同步结果。

### 3.3 明确非目标

- 不是通用团队协作/多用户 SaaS。
- 不自动修改本地代码、创建分支、提交、推送或合并 Git 项目。
- 不自动登录或抓取需要认证的学校系统。
- 不提供疾病诊断、处方或医疗紧急判断。
- 本期不开发原生 iOS/Android 客户端、Apple 日历导入、小米手环接入、通知推送、Docker 打包、Tailscale 配置或真实外部模型/数据源的完整上线接入。
- 不让 Agent 未经确认直接改写日程、取消课程或调整用户承诺。

## 4. 统一业务语言

以下四类对象是产品的共同语言，不替代各模块自己的详情数据。

| 对象 | 含义 | 示例 | 用户动作 |
| --- | --- | --- | --- |
| Event | 有固定时间、通常不可随意移动的事件 | 10:00–11:40 的课程、会议、约会 | 查看、确认改期/取消建议 |
| Action | 可执行、可完成或延期的具体事项 | 完成作业第 2 题、阅读 PRD、购买食材 | 开始、完成、延期、取消 |
| Session | 由多个 Action 组成的结构化计划 | 一次背部训练、课程预习、项目工作块 | 查看步骤、记录结果、确认安排 |
| Signal | 影响排程但不以「完成」为目标的状态 | 睡眠不足、腿部不适、恢复良好 | 记录、查看趋势、修正 |

每个 Event、Action 或 Session 都可以关联时间块与所属模块。一个时间块最终表达为「从几点到几点，做什么，来自何处，是否已确认」。

## 5. 首页：Today Control Console

### 5.1 必须呈现的信息

首页在首屏展示下列内容，不能要求用户先进入聊天或二级页面才看到：

1. 今日日期、当前时间及恢复/休息状态摘要。
2. 今天的时间线：固定 Event 与已确认的工作、学习、训练等时间块。
3. 今天的具体行动列表，按时间、优先级和状态清晰排序。
4. 任务来源/所属模块，例如「课程：机器学习」「项目：EV AI Dashboard」「训练：上肢力量」。
5. 昨日完成度与学习完成度等可量化回顾（仅展示已具备的数据）。
6. 需要用户批准、修订或处理的 Proposal 入口。

AI 对话可以作为独立入口或辅助面板存在，但不是首页的唯一主体，也不得遮挡当天任务和日程。

### 5.2 导航与详情

点击首页项目必须进入其对应详情，而非只打开一张通用 To-do 表：

- 项目 Action → 项目工作页/当前项目 Brief；
- 课程 Event 或学习 Action → 相应课程页与预习/复习材料；
- 训练 Session → 训练计划和动作详情；
- 饮食 Action/记录 → 当天饮食与身体目标页；
- 日程 Event → 日程详情和变更 Proposal；
- Proposal → 证据、影响、冲突与确认/拒绝操作。

### 5.3 07:00 日计划更新

系统在部署机器的本地时间每天 07:00 生成一次当日排程建议。它会读取已确认的 Event、截止日期、课程预习需求、训练/恢复限制和用户偏好，生成新的或调整后的 Proposal。首次当天打开 Dashboard 且还没有恢复记录时，系统可邀请用户完成一个极简 Check-in。

该过程不会自动改变已确认日程，也不在本期主动发送通知。用户打开 Dashboard 后能看见结果并决定是否采用。

## 6. 日程与课表模块

### 6.1 日程骨架

日程以「每一天」和「时间块」为主单元，支持硬事件与软时间块。

- **硬 Event**：课程、会议、约会等固定安排，优先保留。
- **软时间块**：深度工作、课程预习、训练等可协商安排。
- **重复规则**：课程等每周重复安排以规则存储，并生成可管理的日期实例；单日可单独取消、补课或改期，不破坏原规则。

默认排序原则为：硬 Event → 健康/恢复限制 → 用户明确截止日期 → 课程预习 → 训练目标 → 日常习惯和偏好。用户可以为个别事项覆盖该排序。

### 6.2 Agent 协助输入

用户无需手工录入所有时间表。首期需要支持以下交互路径：

1. 用户上传课表截图；日程/课表 Agent 提取课程、时间、地点和重复信息，标记不确定字段，形成待确认 Proposal。
2. 用户以自然语言描述新事项，如「周三下午两点和导师开会」；Agent 解析为候选 Event，并显示时区、冲突和影响。
3. 用户确认后，系统写入或更新日程；拒绝后不写入。

截图识别或自然语言理解产生的结果不能直接生效。每次日程新增、更新、删除、取消或改期都需要明确确认。

## 7. 多 Agent 协作与 Proposal

### 7.1 Agent 角色

| Agent | 负责内容 | 可产生的输出 | 不可做的事 |
| --- | --- | --- | --- |
| 日程协调 Agent | 汇总全局时间、冲突和优先级 | 统一日程 Proposal | 绕过确认写入日程 |
| 项目 Agent | 已授权本地项目的只读分析 | Project Brief、下一步、时间请求 | 改代码、运行修改操作、Git 写入 |
| 课程学习 Agent | 每门课程的学习跟进 | 预习/复习建议、来源、时间请求 | 登录学校系统、把猜测当课程事实 |
| 健身/恢复 Agent | 训练、身体状态、动作计划 | 恢复 Signal、训练 Session Proposal | 医疗诊断、直接排程 |
| 饮食/身体 Agent | 饮食记录、能量与身体目标 | 候选食物记录、每日目标和时间请求 | 把模型猜测当营养事实 |

领域 Agent 不彼此直接争夺日程。它们输出结构化时间请求（目标、时长、时间窗、优先级、限制、理由），由日程协调 Agent 综合后给出单一 Proposal。这样用户只需要面对一个清楚的日程决策面。

### 7.2 Proposal 的基本内容

每个 Proposal 至少说明：

- 建议进行什么变化；
- 依据哪些用户事实、项目/课程数据或公开来源；
- 对今天及相关时间块的影响；
- 发现的冲突与取舍；
- 可选择的确认、编辑、拒绝或稍后处理动作。

Agent 的分析文本与结构化输出必须能够追溯到来源和时间，不把不确定推断包装为事实。

## 8. 项目工作模块：只读 Project Agent

用户可显式授权某个本地项目目录。Project Agent 读取项目代码、Git 状态与提交历史、PRD、技术方案、任务文档和测试结果，并由用户声明或确认该项目目前处于何种生命周期阶段（例如 PRD、技术设计、开发、测试、部署）。

它输出 Project Brief：当前阶段、已完成信号、下一步可执行 Action、依赖/风险、预计时长，以及向日程协调 Agent 提交的时间请求。Git、文档和测试可作为进度信号，但只有用户确认才会正式完成长期项目里程碑或更新里程碑记忆。

项目 Agent 对授权目录严格只读：不得编辑文件、执行会造成修改的命令、创建分支、提交、推送或合并。其价值在于持续理解工作流并帮助拆解与安排，而不是代替用户写入项目。

## 9. 课程与学习模块

### 9.1 课程档案

课表识别后，每门课程建立独立档案和独立记忆空间，包含：课程名称、重复上课规则、课程官网/链接、教学大纲与进度、用户上传材料、作业/考试、当前学习阶段、已知薄弱点与进度。

### 9.2 课前与课后辅助

在即将上课前，学习 Agent 可以基于用户提供的课程网站/材料与自动检索到的公开资料，提出当天课程可能涉及的内容、预习资料、关键概念和复习 Action。建议必须区分：

- 来自官方课程资料的明确内容；
- 来自用户资料的内容；
- 来自公开检索的辅助资料；
- Agent 根据这些来源作出的推断。

首期不自动登录、抓取或绕过需要认证的学校平台。用户可以后续补充课程网站、课程安排和材料来提高建议质量。

## 10. 健身、恢复与身体模块

### 10.1 目标

该模块帮助用户建立可持续的训练计划，结合动作资料、个人目标、历史训练、睡眠/疲劳与不适反馈生成可解释的训练建议。它不替代医生、教练或专业医疗服务。

### 10.2 Fitness Agent 构建流程（产品要求）

首期采用「结构化动作数据 + 检索增强解释 + 本地状态与记忆」的组合，而不是为用户微调模型：

1. **本地数据准备**：导入可审计的健身动作数据库，记录来源、版本和许可；存储动作、目标肌群、器械、难度、注意事项等结构化信息。
2. **用户基础画像**：用户可录入目标、身体数据、训练经验、器械条件、伤病/疾病历史和限制。原始敏感数据保留在本地。
3. **日常 Check-in**：用户以极短方式记录睡眠时长、精力/疲劳和不适。系统将原始记录保存为事实。
4. **状态评估**：确定性规则先计算可解释的恢复因子；模型仅用于理解用户自由文本、解释趋势和组织建议，不能产出诊断结论。
5. **检索与规划**：从本地结构化动作库检索可行训练动作；RAG 仅用于动作解释、用户上传训练资料等非数值知识，不取代动作事实或健康限制。
6. **生成 Session Proposal**：建议目标、动作、组数/次数或时长、替代动作、强度调整原因及所需时间窗。
7. **用户确认与排程**：确认训练 Session 后才向日程协调器提交时间请求；协调器再将其纳入统一日程 Proposal。
8. **执行与学习**：用户记录完成情况、训练感受和不适；Agent 将可追溯的摘要写入本地长期记忆，在后续建议中使用。

当需要调用外部模型 API 时，健康相关的原始记录不会自动整包外发。界面应显示并允许编辑本次调用的 context packet，至少可选「最小必要」与「完整上下文」两档；这是一项外发控制，不等同于每次本地记忆写入的确认。

## 11. 饮食与身体目标模块

饮食/身体 Agent 与健身 Agent 职责分开，但在用户授权范围内共享必要的目标和恢复信息。它负责体重、围度等身体目标，饮食输入、每日能量/宏量营养目标和趋势。

### 11.1 输入与确认链路

首期以自然语言输入为主，例如「午饭吃了 200 克鸡胸肉和一碗米饭」。Agent 解析出候选食物、数量和单位；可替换的 Nutrition Data Provider 查询营养数值；核心计算层计算总热量与营养素；用户确认或编辑候选条目后才保存为正式饮食记录。

模型可帮助理解食物描述，却不能作为营养数值的权威来源。系统不以 RAG 或 LLM 记忆保存可计算的营养事实。对于常见已确认食物、用户自定义食谱和包装食品，本地保存来源/版本快照与复用记录。数据源未来应适配中国食物场景，不承诺只依赖任何单一海外数据库。

## 12. 本地长期记忆

系统采用受 Hermes 持久记忆思路启发的、本地可检查和分域隔离的记忆方式，而不把记忆隐藏在不可见的模型上下文中。每个 Agent/实体拥有范围明确的记忆；共享日程上下文只含经过授权的必要信息。

概念上的本地记忆空间包括：用户画像、日程、项目、每门课程、健身、饮食、共享日程上下文以及按天生成的工作摘要。人类可读的 Markdown 记忆文件让用户可以查看和纠正；业务事实、检索索引、版本、审计与恢复信息由本地数据库维护。具体文件布局、索引和数据库方案属于后续技术设计。

### 12.1 记忆更新边界

| 层级 | 内容 | 默认行为 |
| --- | --- | --- |
| L0 原始记录 | 用户输入、完成记录、Check-in、确认后的饮食数据 | 自动本地保存 |
| L1 日工作摘要 | 当天日程变化、未完成事项、短期上下文 | 自动生成，可压缩或过期 |
| L2 长期摘要 | 稳定偏好、课程/项目阶段、持续训练结论 | 自动整理，保留来源、版本与回滚 |
| L3 高敏感原始信息 | 健康史、不适等 | 自动本地保存，严格按 Agent/外发范围控制 |

直接用户输入和系统观测到的事实可以自动入库；Agent 摘要可自动写入但必须保留版本。公开网页资料、模型推断和医疗相关判断不能自动升级为高影响个人事实。用户可随时在记忆管理页查看、编辑、删除或恢复历史版本；不要求用户逐条审批日常记忆更新。

## 13. 隐私、安全与 API Provider

1. Dashboard、Core、SQLite 与记忆文件运行在用户自己的电脑上。
2. 外部模型 API 是用户自行配置的可替换 Provider。简单生活/学习类任务可使用 DeepSeek 等 Provider；复杂项目只读分析可在用户本地调用 Codex。Provider 细节留待技术设计。
3. 默认不随模型调用发送完整本地数据库、整个项目目录、全部课程材料或完整健康史。每次调用只组装当前任务所需的 context packet。
4. 项目目录访问需按目录获得明确授权；课程材料和健康数据按域隔离；跨 Agent 共享需遵守最小必要原则。
5. 远端 iPhone 访问的目标是私有、安全的浏览器连接。未来部署应使用私有网络/HTTPS 方案，不能把 Core 或 SQLite 直接暴露给公网。
6. 首期不预置「预览账号」。真实 Owner 创建、登录、错误和未配置状态须在界面中真实说明。

## 14. 平台与体验要求

- 首期是网页应用。桌面端和 iPhone Safari/其他手机浏览器都必须可读、可操作、无横向溢出。
- 桌面提供稳定的模块导航和可持续可见的辅助入口；移动端使用真实路由、清晰触摸目标和与桌面一致的数据语义。
- 路由必须支持刷新、返回和前进，不能只通过前端视觉切换假装页面已变化。
- iPhone 远端访问可浏览当天控制台、查看详情、录入反馈、处理 Proposal 和提出问题。
- 可访问性至少覆盖键盘焦点、可辨识状态、触摸目标和错误消息；具体验收阈值在 MVP/技术设计阶段确定。

## 15. 需求清单与验收方向

| ID | 需求 | 验收方向 |
| --- | --- | --- |
| FR-01 | 首页展示当日时间线、日程和模块化具体事项 | 打开首页无需聊天即可看见今日安排；点击进入所属详情 |
| FR-02 | 课表截图导入受 Proposal 约束 | 识别结果可编辑、存在不确定标记；未确认不写入日程 |
| FR-03 | 自然语言事项转日程建议 | 显示解析、冲突和影响；确认后才落盘 |
| FR-04 | 日程按硬/软块与优先级协调 | 同一冲突场景能解释优先级和取舍，用户可覆盖 |
| FR-05 | 每日 07:00 生成但不自动实施建议 | 生成当日 Proposal，未确认的日程不变化 |
| FR-06 | 项目 Agent 只读分析已授权本地项目 | 能输出 Project Brief；测试证明无项目写入行为 |
| FR-07 | 每门课程独立档案与学习建议 | 可关联课程材料/公开资料，建议标注来源与推断 |
| FR-08 | 训练计划受状态与动作库支持 | Check-in 能形成 Signal；Session 在确认前不入日程 |
| FR-09 | 自然语言饮食记录受数据源校验 | 模型解析、Provider 查值、核心计算、用户确认后保存 |
| FR-10 | 分域本地长期记忆可查看/修订/恢复 | 用户能理解来源、修改并撤销记忆；未经授权不外发 |
| FR-11 | 多 Agent 经协调器输出单一日程 Proposal | 领域 Agent 不能绕过协调器直接排程 |
| FR-12 | 桌面与 iPhone Web 可用 | 真实路径、刷新/后退、触摸与可读性均通过测试 |
| FR-13 | API 配置入口与未配置诚实状态 | 用户能配置 Provider；未配置时无伪造回复或成功状态 |

## 16. 现阶段产品反馈的可追溯性

此前 Demo 暴露的两项关键反馈将由本 PRD 约束后续设计：

| 反馈 | 本 PRD 对应要求 |
| --- | --- |
| 没有可配置 API 的入口 | FR-13；Provider 可替换、未配置状态明确且不伪造回复 |
| 任务系统像普通 To-do，无法跟进项目、课程和生活流程 | FR-01、FR-06、FR-07、FR-08、FR-09、FR-11；任务必须落在模块上下文和时间块中 |

## 17. 版本边界与后续流程

本文件批准前，任何现有 Demo 或 v0.2 原型仅作为技术探索，不是最终产品定义。产品流程固定为：

1. 审核并批准本 PRD；
2. 协作确定 MVP 具体范围与验收标准；
3. 基于已批准 MVP 制作高保真交互 Demo，使用受控示例数据，不伪装为真实外部集成；
4. 审核 Demo 后编写 `TECH_SPEC.md`、`ARCHITECTURE.md`；
5. 拆解 `TASKS.md`，再进入分片开发、测试、部署、可观测性和反馈迭代。

MVP 尚未在本文冻结。确定 MVP 时需要选择每个模块是否进入首期闭环、哪些数据是受控样例、哪些是本地真实写入、以及外部 API/数据 Provider 的第一批接入边界。

## 18. 当前工程约束（供后续技术阶段参照）

当前仓库已有 TypeScript 多包原型（contracts、domain、core、web），并存在既有 v0.2 分支/PR。后续技术设计应决定是否保留或重构这些实现，不能以现有 UI 限制本 PRD。

常用验证命令：

```powershell
npm install
npm run dev:core
npm run dev:web
npm test
npm run typecheck
npm run lint
npm run build
npm run test:e2e
```

本 PRD 草稿建立时，在隔离分支上执行 `npm test` 的基线并未全绿：Core 共有 14 个失败测试，Web 测试启动还报告缺少 `@vitejs/plugin-react`。本文没有为规避该结果修改任何代码；该问题必须在后续测试/技术计划中先做根因诊断与处置，不能被当作通过基线。

后续开发必须遵守：先写规格和验收、以测试驱动关键行为、每个改动独立验证、避免提交密钥或用户数据；涉及数据库迁移、新外部服务/凭据、公开网络暴露或破坏性数据操作时，须在实施前重新确认。
