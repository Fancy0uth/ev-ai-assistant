## 真实路径与测试替身边界

scripts/run-e2e.mjs 只在受管 E2E 中显式启动 apps/core/e2e/daily-plan-test-bootstrap.ts，并设置 EV_E2E_DAILY_PLAN_TEST_BOOTSTRAP=1。普通 apps/core/src/server.ts 从不导入该文件，因此生产启动不可能使用 Fake Provider 或 Fake credential port。

该 bootstrap 调用真实 buildApp，仅注入确定性 Fake DailyPlanningProvider 与 test-only SecretStorePort。Provider 只接受该 E2E 的 60 分钟请求并产生本地校验通过的建议。对真实生成请求，bootstrap 在 runner-owned SQLite 中临时写入不可逆 marker credential，供真实 credential service 读取后立即删除；不会写入 Fake Provider key、真实 key 或浏览器可见 credential。

查询参数 e2eWithoutTestCredential=1 只由该 test-only bootstrap 识别，用于证明未注入 marker 时真实 Core 生成路由仍诚实返回未配置的 409。普通服务器不识别、也不需要该开关。认证、Web proxy、Core HTTP 解析、Context、校验、持久化、review decision 和列表读取均保持真实。

## 浏览器错误门禁

页面持续收集全部 console warning/error、pageerror 和页面 401，并默认全部失败。唯一的例外已被明确、逐次断言：

1. 仅在测试刚为该 Proposal 的真实 stale decision URL 预先 armed 后。
2. 仅接受 Chromium 的精确原生日志：Failed to load resource: the server responded with a status of 409 (Conflict)。
3. 日志 location 必须是该唯一 decision URL，且同一 URL 的实际响应已断言为 409 DAILY_PLAN_BASE_VERSION_STALE。
4. 每个 desktop stale flow 必须且只能出现一次该日志。

这不是全局 409/error ignore；任意其他 console warning/error、pageerror 或 401 仍会使测试失败。原因是 Chromium 对该必需且已验证的 fetch 409 自动发出 resource diagnostic；该日志在附件中以 [expected-stale-409] 明确保留。

## 可复现操作与 API 错误检查

1. 执行 npm run test:e2e。runner 独占端口、临时数据目录、Core test bootstrap 和 Web，并在成功后删除数据目录。
2. 建立隔离 Owner；不注入 marker 的真实生成请求返回 409 DAILY_PLAN_PROVIDER_NOT_CONFIGURED。
3. 对 desktop/iPhone 的不同日期写入两个稳定排序的 TimeRequest，打开 /daily-plan，点击“生成每日计划”。
4. 断言真实 browser generation response 为 201 和随后的 proposal-list read 为 200；编辑请求 1 为 13:00–14:00，只点击该项“采用安排”。
5. 在决策响应及 reload 后的实际 list read 中断言 PARTIALLY_APPLIED/APPLIED/PENDING_REVIEW；验证一个编辑后的软 Event、没有第二个 Event 和无关同日期 OPEN Task 不变。
6. 对 desktop stale 草案，先写入硬 Event，再点击可见“采用安排”；断言真实 409 DAILY_PLAN_BASE_VERSION_STALE、页面 stale alert/status、禁用控件及精确 Event 集。
